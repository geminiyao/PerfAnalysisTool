本 prompt 是数据源无关骨架，报告章节结构通过 `{{REPORT_TEMPLATE}}` 占位符注入。
启动时框架按 `ReportPipeline.reportTemplatePath` + `detectStateMode()` 选模板填入：

**注入的模板只定义章节骨架 + 写作纪律，不是填空模板**。你按模板的章节结构组织 sections，
但每个 section 的内容（intro/items/narrative）由你根据 findings 推理写，不是抄模板。

★【sections 必须建全模板要求的所有章节·不许漏章】
模板（{{REPORT_TEMPLATE}} 注入）定义的章节骨架，你的 sections 数组必须建全，每个 section 的 heading 以模板要求的章节标识开头（如 perfetto 模板的 §0-§7）。
漏建任何一章 = 报告结构残缺。
即使某章内容不多，也要建 section（intro 一句话 + 1 个 item 即可），不要跳过。

★【item.visualAsset 填视觉资产·按模板要求填】
模板的 §1/§2/§4/§5 等章节要求填视觉资产（表格/矩阵/ASCII 图）时，在该 section 的 item 里填 `visualAsset` 字段。
visualAsset 是通用的（不硬编码 perfetto 特有概念），三种类型：
- type="table"：表格（headers + rows），如 §1 采集元信息、§2 多线程宏观、§5 红线触发清单
- type="matrix"：矩阵（带 levelColumn 按 confirmed/likely/suspected 上色），如 §4 降频判定矩阵
- type="ascii"：ASCII 图（content + caption），如 §3 状态分布图/因果链图

item.visualAsset 结构：
```json
{
  "findingIds": ["..."],
  "title": "...",
  "narrative": "...",
  "visualAsset": {
    "type": "table",
    "title": "采集元信息",
    "table": { "headers": ["指标","值"], "rows": [["帧数","683"],["fps","59.8→33.1→21.4"]] }
  },
  "severity": "info"
}
```
type="matrix" 时多一个 levelColumn 字段（指向 headers 里某一列，该列值是 confirmed/likely/suspected）。
type="ascii" 时用 ascii 字段（不用 table）：`"ascii": {"content": "...", "caption": "..."}`。

render 会把 visualAsset 渲染在 item 的 narrative 下方、callTree 上方。
模板要求填视觉资产的章节，item 必须填 visualAsset——不填 = 报告缺表格/矩阵/图。

【叙事的灵魂 · 这不是把 findings 换个格式重贴一遍】
═══════════════════════════════════════════════════════════════

作文机式报告好在"叙事流"——你要超过它：

1. **概览讲一个故事，不是甩发现**：一句话说清这次采集的整体性能故事。
   例："这不是单一元凶，是一组稳态开销（行军线+UI+渲染）每帧雷打不动吃掉近7ms打底，再被相机移动、GC等偶发尖峰反复捅刀。"

2. **问题先行 + 按"对整体帧率的贡献"排序**（★关键，别犯老错）：
   排序看"对整体帧率的贡献"，**不看"单帧数字多吓人"**。一个每帧稳定2.3ms的开销(600帧累计1.38秒)，
   比一次70ms但仅出现1次的GC对平均帧率的拖累大得多。**GC.Collect只出现2-3帧，就不该排在稳态大头前面。**
   算贡献：稳态项看"每帧ms×出现帧数=累计总量"；尖峰项看"命中多少帧、占极慢帧多大比例"。

   **三维显式标注**（★每个 topConclusion 必须标，别只写 contribution 文字）：
   除 contribution 外，给每条热点标 `dimensions` 和 `judgability`：
   - **绝对量大 (absoluteCost)**：占帧预算显著（如 2.3ms/帧 占 16.6ms 预算的 14%）——能判整体达标与否的硬指标。
   - **占比高 (shareHigh)**：占总 CPU / 累计总量（如"每帧2.3ms×600帧=1381ms，全场self最高"）——已在 contribution 里体现，dimensions 里也要标。
   - **离群严重 (outlier)**：自己跟自己比的内生 baseline（spikeRatio 高、p99/mean 大）——发现"偶发炸"。
   一条热点可同时标多个维度（如 ["outlier","shareHigh"]）。
   `judgability` 标这条结论单源能不能下定论：
   - **judgable**：能判——有绝对基线(16.6ms/60fps)或本次采集内内生可比（相对大小/离群度）。
   - **needsBaseline**：该不该管需历史基线 diff，单源结构判不了。
   - **needsDomainKnowledge**：需业务知识才能判断"正不正常"，单源判不了。
   正例：{"rank":1,"problem":"相机移动必卡","kind":"高频尖峰","contribution":"19次移动100%命中极慢帧,占极慢帧70%","dimensions":["outlier","shareHigh"],"judgability":"judgable","severity":"critical"}

3. **判定边界诚实声明**（★超越作文机的"知道自己边界"）：
   报告必须有一处诚实声明——单源这次**能判什么、判不了什么**，写进 `judgmentBoundary` 字段：
   - **canJudge**：单源能确定的（整体超没超 16.6ms 预算、各项相对大小/离群度、本次采集内谁最大）。
   - **cannotJudge**：单源判不了的（单个 marker"这笔开销该不该管/正不正常"——需历史基线 diff 或业务知识）。
   正例：{"canJudge":["整体帧时中位数X ms,超/未超16.6ms预算","相机移动是本次采集内离群最严重的尖峰源"],"cannotJudge":["行军线每帧2.3ms在本游戏压测下算不算正常——需历史基线或业务知识,单源判不了"]}
   ❌ 反例：把"判不了该不该管"的项硬写成"这是问题必须优化"——违背诚实标注。
   ❌ 反例：因为"单源判不了该不该管"就对所有热点不给任何 dimensions 定性——降级链要求至少给通用三维。

   **热点判定降级链**（可插拔，不许因缺参照就瘫痪）：
   判断"热点该不该管"时按此顺序降级——有业务知识用知识判 → 没有 fallback 历史基线 diff → 再没有 fallback 通用三维 + 诚实标注判不了。
   **当前单源无历史基线、无知识回路**，所以实际走"通用三维 + 声明判不了"这一档：
   必须给 dimensions 三维定性（至少标能标的那几类），同时 judgability 和 judgmentBoundary 里诚实说"该不该管"判不了。
   **不许假装能判，也不许因缺参照就不给任何判断。**

4. **按主题分群，不按发现序号**：把发现归类成有共性的组，每组给一段导语讲共性。典型分群：
   - "稳态开销群"（每帧都在的常驻税，决定天花板）——合起来讲"这几项合计每帧X ms"
   - "偶发尖峰群"（低频但制造顿挫的）——合起来讲
   - "工作线程"（★别只盯主线程！Job.Worker/Submit/Render 线程的开销也要看，主线程的等待往往是在等这些线程）
   - "已排除"（查证后确认不是问题的——这是你强过作文机的地方：敢说"这个不用管"）
   分群和顺序**你自己定**，怎么讲这个故事最清楚就怎么分。

   ★【多线程宏观章节必须覆盖 findings 里所有识别线程】
   threadOverview 字段必须包含 findings 里出现过的所有线程类型（不只 UnityMain）。
   每个 threadOverview 行的 runPct/sleepPct/runnablePct 从 findings 的 querySchedState evidence 取。

   规则：
   - findings 里 querySchedState 查过的每个线程类型，threadOverview 都要有一行
   - 没有 sched 数据的线程不许编——如果 explore 没查某线程，threadOverview 里就不列（但要在 judgmentBoundary.cannotJudge 声明"X 线程未覆盖"）
   - Audio/Sleep ≥99% 的线程也要列进 threadOverview，note 标"非瓶颈，Sleep ≥99%"
   - 每个线程的 note 给一句话定位（如"主线程，业务/Lua/ECS 调度主入口"/"Render 命令录制层，等主线程发命令"/"RHI 直调 driver，三态 run% 单调下降"）

5. **跨发现串联**：发现之间的关系要讲出来。例："主线程的present等待(0.95ms/帧)在等Submit线程的Gfx.PresentFrame(8.82ms/帧)——
   说明渲染/GPU压力本身就大，不全是CPU脚本的锅。"这种串联是模板套不出来的，是你的价值。

6. **源码归因**：读到真实代码的发现，把代码里的具体问题讲出来（如"OnUpdate里三个每帧全量foreach：xxDict/yyDict"）。
   没读到源码的诚实说"未能定位到行级"，别硬编。

  - 如果父模块下的子节点都比较平均（没有绝对大头）→ **统筹在父模块**，hotspot 列列前 2 个子节点，**子节点不许单独列**
  - 如果父模块下有明显大头子节点 → **拆分出大头子节点**，不列父模块
  - **递归**：拆分出来的大头子节点，如果它下面还有明显大头子节点，继续拆分；如果它下面子节点比较平均，就统筹在它

  ★【统筹与拆出互斥·不许混用】
  对同一个父模块，要么统筹（列父模块 + hotspot 列子节点），要么拆出（列大头子节点 + 不列父模块）——**不能同时列父模块和子节点**。
  ❌ 反例（v4 退化重犯，混用）：列了 LuaMgr（hotspot="BattleHeadMgr + MapSignificanceMgr"）+ 又列 BattleHeadMgr.OnUpdate + 又列 MapSignificanceMgr.ProcessTasks → LuaMgr 的开销被算了两次（一次在 LuaMgr 行，一次在子节点行）
  ✅ 正例（统筹）：只列 LuaMgr（hotspot="BattleHeadMgr 4.92% + MapSignificanceMgr 3.99%"），子节点不单独列
  ✅ 正例（拆出）：只列 BattleHeadMgr.OnUpdate + MapSignificanceMgr.ProcessTasks，LuaMgr 不列（因为子节点要单独拆出）

  ★【红线清单归并 ≠ 下钻独立·两个维度别混】
  - **红线清单**（visualAsset.table）：遵守归并规则，父子不同时列。LuaMgr 下子节点比较平均 → 统筹在 LuaMgr，子节点不单独列。
  - **下钻 items**（§5 的 items，不是红线清单）：每个值得下钻的模块都可以独立下钻，**不受红线清单归并约束**。
  - 即：红线清单可以只列 LuaMgr（统筹），但 §5 仍然可以独立下钻 BattleHeadMgr/MapSignificanceMgr（下钻 item 给 callTree.rootMarker）。
  - ❌ 错误理解："下钻要独立 = 红线清单也要独立列子节点"——红线清单归并和下钻独立是两个维度，别混。

  callTree 真实父子关系（从 Core.Update 下钻）：
  ```
  Core.Update
  ├─ CS:AOE.LuaMgr                    ← 12.51%（大头，拆出，不列 Core.Update）
  │  ├─ BattleHeadMgr.OnUpdate        ← 4.92%（LuaMgr 下的子节点）
  │  └─ MapSignificanceMgr.ProcessTasks ← 3.99%（LuaMgr 下的子节点）
  └─ CS:AOE.Outside.MapManager        ← 9.54%（大头，拆出，不列 Core.Update）
     ├─ OutSideViewArmyLineMgr        ← 5.19%（MapManager 下的大头，拆出，不列 MapManager）
     └─ BattleUIManager               ← 2.38%（MapManager 下的子节点）
  ```

  正确归并（递归拆大头，统筹与拆出互斥）：
  - CS:AOE.LuaMgr 12.51%（hotspot="BattleHeadMgr 4.92% + MapSignificanceMgr 3.99%"）← LuaMgr 下子节点比较平均，**统筹在 LuaMgr**，BattleHeadMgr/MapSignificanceMgr **不许单独列在红线清单**
  - OutSideViewArmyLineMgr 5.19%（hotspot="CalculateVertexJob"）← MapManager 下的大头，**拆出**，MapManager 不列
  - BattleUIManager 2.38% ← MapManager 下的子节点，MapManager 已被 OutSideViewArmyLineMgr 拆出替代，BattleUIManager 可独立列（它的父 MapManager 不在清单里）
  - **不许同时列** LuaMgr 和 BattleHeadMgr（父子关系）
  - **不许同时列** LuaMgr 和 MapSignificanceMgr（父子关系）
  - **不许同时列** MapManager 和 OutSideViewArmyLineMgr（父子关系）

  但"不列父模块"不等于"只列父模块"——必须细到子模块，不许只列 Core.Update 一行（v4 退化教训）。

narrative.json 必须包含 `narrativeProvenance` 字段，标记这份 narrative 是谁产出的。
渲染器（render-html）会校验 `generatedBy === "LLM"`——脚本拼的 narrative.json 会被拒绝渲染。

在 narrative.json 顶层加：
```json
"narrativeProvenance": {
  "stage": "narrative-llm",
  "promptVersion": "narrative-prompt.txt@v1",
  "generatedBy": "LLM"
}
```

- `stage` 固定 `"narrative-llm"`（标记产出阶段）
- `promptVersion` 固定 `"narrative-prompt.txt@v1"`（标记 prompt 版本）
- `generatedBy` 固定 `"LLM"`（你是 LLM，不是脚本；脚本拼的会被拦截）

漏写或写错 = 渲染器拒绝渲染这份 narrative.json。
