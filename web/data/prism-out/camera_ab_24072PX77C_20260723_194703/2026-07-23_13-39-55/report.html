§0 结论先行：三组问题合谋把帧率从 60 压到 22

按对整体帧率的贡献排序，3 条核心结论。稳态回归（Update + LateUpdate + URP）是天花板压低的主因，相机移动和 GC 是制造顿挫的尖峰。

① 主线程脚本双路径回归——Update 涨 10.5 倍 + LateUpdate 涨 8.4 倍，每帧多吞 17.7ms 严重

这是退化的头号元凶，合占 PlayerLoop 退化的 65%。 Update 路径从基线 1.22ms 涨到 12.88ms/帧，LateUpdate 从 0.82ms 涨到 6.86ms/帧——两路加起来每帧多吞 17.7ms，直接把 p50 从 16.66ms 顶到 41.92ms。大头是 Lua 侧的地图实体显著性管理（MapSignificanceMgr，每帧 4ms）和 C# 侧的行军线管理（OutSideViewArmyLineMgr，每帧 2.84ms），都是每帧全量遍历被场景实体数压垮。基线同结构仅 1.2ms/0.82ms，说明不是代码劣化而是工作量×全量遍历的叠加。详见 §3 下钻 ①②。

§2 多线程宏观：主线程是退化主战场，Submit 线程跟着变长杆

UnityMain 退化最重（业务/Lua/渲染调度全在这里），Submit Thread 和 Render Thread 跟着从『早早完成』变成长杆，Job.Worker 池和 LuaMtGC 是偶发尖峰源不是稳态瓶颈。

多线程宏观 信息

三个主力线程 ms/帧 都从 16.66 翻到 44.6——但含义不同：UnityMain 是真在算（脚本回归），Submit/Render Thread 是被主线程的渲染命令和 GPU 提交同步拉长。Job.Worker 池多数帧空闲，仅偶发 UI 几何重建尖峰。LuaMtGC 偶发 21.6ms 单帧爆。主线程的 Semaphore 等待 p50 0.77ms 健康，说明主线程多数帧不等 GPU——不是 GPU-bound，是脚本 bound。

§3 主线程一帧时间去向：脚本 + 渲染 + 尖峰的三层构成

先看 PlayerLoop 帧分位数和红线触发清单总表，再对每个红线条目独立下钻。归并原则：父子不同时列，大头拆出（MapSignificanceMgr 从 LuaMgr 拆出、OutSideViewArmyLineMgr 从 MapManager 拆出），分摊型统筹在父（URP.Render 统筹 4 pass）。

红线触发清单（按占 p50% + foldChange 排序） 严重

红线清单按『占 p50 ≥5% 或 foldChange ≥2』判定。稳态项按每帧 ms/帧 排序，尖峰项按单次 ms 排序。归并：Core.Update 下 LuaMgr 6.82ms + MapManager 4.84ms 两个大头语义不同（Lua 调度 vs C# 地图管理）→ 各自独立拆出，Core.Update 不列；LuaMgr 下 MapSignificanceMgr 3.99ms 是大头 → 拆出，LuaMgr 不列；MapManager 下 OutSideViewArmyLineMgr 2.84ms 是大头 → 拆出，MapManager 不列；URP.Render 下 4 个 pass 语义相同（同属渲染管线）且分摊无大头 → 统筹在 URP.Render。

下钻 ① MapSignificanceMgr：每帧 3.99ms 的地图实体显著性管理，被场景实体数压垮 严重

Update 路径最大叶子，每帧 3.99ms，占 p50 9.5%。 它是 Lua 侧管理地图实体『谁该显示/谁该隐藏』的调度器，内部 EntityTask 每帧 3.57ms 分成三个任务：MapEntityAdd 1.55ms（处理实体新增）+ MapObjRefresh 1.20ms（刷新现有实体）+ CleanUp 0.47ms（清理过期实体）。基线同结构在 LuaMgr.OnTick&UpdateSchedule 下只占很小一块，当前态实体数显著增加后被全量遍历压垮。GC 归因：Update 路径 GC alloc 计数从 4777 涨到 51365（×10.75），但 gc_allocated_in_frame 均值仅 19KB——是『大量极小对象分配』，疑似 Lua→C# 跨边界每帧大量装箱/临时 List。优化方向：ProcessTask_MapEntityAdd/MapObjRefresh 是逐帧全量处理，建议改增量/分帧（按预算节流每帧只处理 N 个），或对实体做脏标记避免全量 Refresh。Lua 下层函数体当前 profiler 采样不到，需 Lua profiler 进一步下钻确认具体 Lua 回调。
