核心结论
#问题类型对整体贡献严重度
1 throttle 态主线程 38% 时间在干等 GPU，单次等 17.8ms 已超 vsync 周期 稳态大头 throttle 态等 GPU 占窗口 38.1%（7600ms），427 帧平均每帧等 17.8ms，单次已超 16.67ms vsync 周期；三态单调恶化 base 5.4%→cur 19.2%→throttle 38.1%，是帧率从 60fps 崩到 21fps、98.83% 帧超预算的首要成因 严重
2 SoC 热限流：大核频率被压到 59%，中核 max 频率从 2419MHz 降到 2227MHz 伴随恶化 大核 reach 74.9%→75.6%→59.2%（throttle 暴跌破 65%），中核观测 max 从 cpuinfo 上限 2419MHz 被压到 2227MHz，温度三态持续 75-79°C；是 GPU-bound 的加剧因素而非独立主因，与 GPU 满载发热形成恶性循环 高
3 主线程越来越闲但帧越来越慢：run 86.9%→57%，帧时却 16.7→45.9ms 宏观佐证 主线程 runningPct 三态单调下降 86.9%→77.8%→57.0%，sleepingPct 单调上升 12%→20.4%→39%；闲下来的时间几乎全部是等 GPU（wait slice 占比同步 5.4%→19.2%→38.1%），与 GPU-bound 判定互印证 信息
4 Core.Update 业务模块涌现是场景差异不是性能退化 场景澄清 base 是空场景（Core.Update 内无战斗/行军 marker），cur/throttle 是战斗+行军压测，业务模块 foldChange=9999 是 base 无数据的伪信号；cur→throttle 同场景对照 BattleHeadMgr 731→471ms、MapSignificanceMgr 627→456ms 反而略降，无系统性恶化 中
5 渲染管线内部持续 GC 分配（URP.BeforeRendering + OpaquePass 每帧上百次） 长期风险 cur 每帧 130+129 次分配（共 208568 次），throttle 每帧 31+30 次（共 59518 次）；GC.Collect 实际只触发 3次/1次占总窗口 <0.4%，当前不是帧时主因，但持续分配挤压 GC 堆是长期卡顿风险 低
已排除 Render 线程瓶颈: UnityGfxRenderS runningPct 从 base 25.98% 降到 throttle 16.71%，CPU 渲染链路变闲不是瓶颈，反向佐证压力在 GPU 侧Choreographer / SurfaceFlinger 问题: 三态 Choreographer 都稳定 60fps / slowFrameRate=0，合成侧健康binder / IO / 锁阻塞: throttle 态主线程 off-CPU 中 D 状态（不可中断睡眠）仅 1.3%，IO/锁/binder 阻塞可排除业务模块性能退化: cur→throttle 同场景对照 BattleHeadMgr 731→471ms、MapSignificanceMgr 627→456ms 反而略降，Core.Update 3537→3436ms 也略降，业务侧无系统性恶化；foldChange=9999 是 base 空场景无数据的伪信号
主题分群
§1 采集元信息：三态从 60fps 退化到 21fps

三态采集对照，帧预算 16.67ms（60Hz vsync 周期）：

| 指标 | base | cur | throttle |
|---|---|---|---|
| PlayerLoop p50 | 16.69ms | 30.15ms | 45.94ms |
| PlayerLoop p99 | 21.37ms | 42.54ms | 66.32ms |
| FPS | 59.8 | 33.1 | 21.4 |
| slowFrameRate | 0% | 11.18% | 98.83% |
| 采集后温度 | 77.3°C | 79.0°C | 76.7°C |

base 刚好踩在 60fps 线上（p50 16.69 ≈ 预算），cur 已掉到 33fps（p50 近 2 倍预算），throttle 彻底崩到 21fps（p50 近 2.75 倍预算、几乎所有帧超预算）。温度三态都在 75°C 以上，throttle 已进入持续热稳态。

三态帧时演化：从健康到病态的单调恶化 严重

三态构成一条清晰的退化轨迹：base 是凉机起步的健康态（p50 踩线 60fps），cur 是升温后的中等 GPU-bound（p50 30ms、slowFrame 11%），throttle 是持续热限流下的病态（p50 46ms、98.83% 帧超预算）。p50 与 p99 的差距（throttle 45.94 vs 66.32）说明慢帧是稳态而非偶发尖峰——不是个别帧被卡，是几乎每帧都慢。

源码归因未定位到行级源码，帧时数据来自 PlayerLoop 调度计数器。
优化建议
  1. 以 throttle 态为优化基线——它代表设备在热稳态下的真实表现，不是最差尖峰

UnityMain：从 86.9% 忙到 57% 闲，闲在等 GPU 而非无事可做 信息

主线程 runningPct 单调下降 86.9%→77.8%→57.0%，sleepingPct 单调上升 12%→20.4%→39%。关键判读：主线程不是'干活变慢'而是'越来越多时间在等待'——off-CPU 归因显示 throttle 态 Sleep 中 89.34% 是可中断睡眠（S 状态），仅 1.3% 是不可中断（D 状态，IO/锁），wait slice 重叠法证明 Sleep 的增量几乎 100% 是等 GPU。R+（被抢占）从 0.42% 升到 2.78%，与降频期间大核不足、任务排队增多一致，是降频的伴随现象。

源码归因未定位到行级源码，调度状态来自 sched 分析。
优化建议
  1. 无需独立优化主线程 idle——解决 GPU-bound 后 idle 比例自然回落
UnityGfxRenderS：渲染线程变闲，CPU 渲染链路不是瓶颈 信息

渲染线程 runningPct 从 base 25.98% 降到 throttle 16.71%、sleepingPct 升到 79.85%。如果瓶颈在 CPU 渲染链路（DrawCall 提交 / 渲染状态设置），渲染线程应该更忙才对；它反而变闲，说明 CPU 侧的渲染提交不是阻塞点，压力在 GPU 侧——这是 GPU-bound 判定的关键辅证之一。

源码归因未定位到行级源码，调度状态来自 sched 分析。
优化建议
  1. 渲染线程无需优化——它不是瓶颈，优化 GPU 侧负载才会让渲染线程重新忙起来
§3 主线程 off-CPU 归因：89% 是 Sleeping，核心是等 GPU

throttle 态主线程 off-CPU byState 分布：

| 状态 | 占 off-CPU | 含义 |
|---|---|---|
| S（可中断睡眠） | 89.34% | 等待资源/信号量，绝大多数是等 GPU |
| R（就绪未跑上） | 6.58% | 想跑但没 CPU，降频期间大核不足 |
| R+（被抢占） | 2.78% | 跑了一半被抢，任务排队 |
| D（不可中断） | 1.30% | IO/锁阻塞，已排除 |

wait slice 重叠法（核心证据）：

```
主线程 Sleeping 总量 vs Gfx.WaitForPresent 总量（throttle 态）
Sleeping 总量 ████████████████████████████████ 7666ms
Gfx.WaitForPresent ██████████████████████████████ 7600ms
重合度 ██████████████████████████████ ~99%

→ Sleep 增量几乎 100% 是等 GPU，binder/IO/锁只占 1.3%（D 状态）
```

因果链（throttle 一帧的等待链路）：

```
UnityMain 发起渲染提交
│
▼
URP.Submit (throttle 8069ms, foldChange ×124.5)
│
▼
Gfx.WaitForPresentOnGfxThread (单次 avg 17.8ms，超 vsync 16.67ms)
│ 主线程在此阻塞，干等 swapchain
▼
Semaphore.WaitForSignal (叶子，等 GPU 完成一帧)
│
▼
GPU 完成 → swapchain 提交 → 主线程被唤醒
```

wait slice 重叠：主线程 Sleep 的增量几乎 100% 是等 GPU 严重

三态 Gfx.WaitForPresentOnGfxThread 单次 avg 从 0.9ms → 5.83ms → 17.8ms，对照 60Hz vsync 周期 16.67ms：base < 35%（健康），cur 35%~100%（中等 GPU-bound），throttle > vsync（强 GPU-bound critical，swapchain 撑爆）。Sleep 增量（base 1351ms → throttle 7666ms，增量 6315ms）≈ wait slice 增量（624→7608ms，增量 6984ms），核心增量是等 GPU。URP.Submit 的 foldChange 高达 ×124.5（base 64.8ms → throttle 8069ms），是三态涨幅最大的 slice，直接指向渲染提交链路被 GPU 拖累。

优化建议
  1. GPU 侧根因需 GPU counter / RenderDoc 截帧才能定位（DrawCall 过多 / Shader 复杂 / 分辨率 / 渲染负载）
  2. 检查 URP.RenderCameraStack count=854（throttle 每帧约 2 个 camera），确认是否有不必要的多相机渲染
  3. URP.MainRenderingTransparent throttle 727ms（3.64%），透明渲染 pass 值得排查
排除项：binder / IO / 锁阻塞只占 1.3% 信息

D 状态（不可中断睡眠，IO/锁/binder 阻塞标志）在 throttle 态仅占 off-CPU 的 1.3%，可以排除 binder 调用阻塞、文件 IO、锁竞争等常见主线程卡顿源。R+（被抢占）从 base 0.42% 升到 throttle 2.78%，是降频期间大核不足、任务排队增多的伴随现象，不是独立阻塞点。

源码归因未定位到行级源码，byState 来自 sched 状态聚合。
优化建议
  1. 无需排查 binder/IO/锁——数据已排除
§4 降频时序：大核 59%，中核 max 被压低，温度 75-79°C

三态降频对照表：

| 指标 | base | cur | throttle |
|---|---|---|---|
| 大核 reach%（vs cpuinfoMax） | 74.9% | 75.6% | 59.2% |
| 大核 avg MHz | 1729.5 | 1576.3 | 1324.6 |
| 中核 reach% | 76.1% | 71.8% | 52.4% |
| 中核观测 max MHz | 2419.2 | 2342.4 | 2227.2 |
| 中核 cpuinfoMax MHz | 2419.2 | 2419.2 | 2419.2 |
| 采集前温度 | 65.6°C | 79.8°C | 75.6°C |
| 采集后温度 | 77.3°C | 79.0°C | 76.7°C |
| 温度 Δ | +11.7°C | -0.8°C | +1.1°C |

降频形态（三态演化）：

```
形态 1: base — 凉机起步快速升温
特征: 起点 65.6°C → 终点 77.3°C (Δ+11.7°C)，大核 reach 74.9% 健康
推断: 凉机起步，快速升温进入热保护区间，尚未限流

形态 2: cur — 高温饱和
特征: 起点 79.8°C 已饱和，大核 reach 仍 75.6%，中核 max 开始下调 2419→2342
推断: 起点已热，中核 max 被压是 SoC 限频的早期信号

形态 3: throttle — 持续热限流
特征: 大核 reach 暴跌至 59.2%（<65%），中核 max 2227MHz（<cpuinfo 2419），温度 75-77°C 稳态
推断: SoC 主动压低 max-freq + 大核 reach 不足，持续热限流
```

SoC 热限流：大核被压到 59%，中核 max 频率主动下调 高

throttle 态大核 reach 暴跌至 59.2%（base 74.9% → cur 75.6% → throttle 59.2%），中核观测 max 从 cpuinfo 上限 2419MHz 被压到 2227MHz——这是 SoC 主动压低 max-freq 的间接证据（理论上限不可达）。三态温度演化构成'凉机起步 → 高温饱和 → 持续热限流'的形态：base 起点仅 65.6°C 采后升到 77.3°C（Δ+11.7°C，凉机快速升温），cur 起点已 79.8°C（起点已饱和），throttle 持续 75-77°C（高温稳态）。降频是 GPU-bound 的加剧因素：GPU 满载发热 → SoC 热限流 → CPU 降频 → 主线程可用算力更少 → 帧更慢 → 积压更多，形成恶性循环。

调用树备注
大核集群 reach 59.2%，avg 1324.6MHz；中核 cpu4-6 max 被压到 2227MHz（<cpuinfo 2419）
源码归因未定位到行级源码，频率来自 cpu_freq trace，温度来自 summary beforeC/afterC（thermal sidecar 实际是占位符）。
优化建议
  1. 短期：优先解决 GPU-bound，GPU 负载降下来温度自然降
  2. 长期：看是否有画质档位可动态降级（AOE3D 有 5 档画质），在温度超阈值时自动降档
  3. 检查渲染分辨率（移动端 900p）是否可在热态时动态下调
  4. 需要看项目的温控策略代码和画质档位配置才能给具体建议

主线程 callTree 缩进树（Core.Update 三态对照）：

```
Core.Update base 1177 / cur 3537 / throttle 3436 ms (占比 10.3% / 24.1% / 17.2%)
├─ [base 内无战斗/行军 marker — 空场景]
├─ CS:AOE.Outside.OutSideViewArmyLineMgr base ~0 / cur 761 / throttle 1042 ms/帧区间 (📈 cur 涌现 → throttle 涨 37%)
│ └─ OutsideLineCtrl:CalculateVertexJob (Burst) throttle 260ms / 51240 次 (行军线 vertex 并行计算)
├─ BattleHeadMgr base ~0 / cur 731 / throttle 471 ms (📈 cur 涌现 → throttle 降 36%)
├─ MapSignificanceMgr base ~0 / cur 627 / throttle 456 ms (📈 cur 涌现 → throttle 降 27%)
└─ CS:AOE.Outside.MapManager base 298 / cur — / throttle — (base 即有，行军管理基座)
```

关键判读：base 的 Core.Update 内部只有 LuaMgr (678ms) + MapManager (298ms)，没有战斗/行军相关 marker——base 是空场景采集。cur/throttle 的业务模块涌现是场景差异（战斗+行军压测），不是性能退化。cur→throttle 同场景对照，BattleHeadMgr 和 MapSignificanceMgr 反而略降，OutSideViewArmyLineMgr 涨 37%（761→1042ms）是行军压测压力增大，不是异常。

OutSideViewArmyLineMgr：行军线管理在 throttle 涨 37%，是行军压测的正常负载 中

OutSideViewArmyLineMgr 在 throttle 占 5.22%（1042ms），其子节点 OutsideLineCtrl:CalculateVertexJob (Burst) 占 1.31%（260ms，51240 次调用），是 Burst 并行计算的 vertex 生成——行军场景的正常成本。cur→throttle 涨 37%（761→1042ms）对应行军压力增大，不是性能退化。foldChange=9999 是 base 无数据的伪信号（base 是空场景，Core.Update 内根本没有这个 marker），不能当退化证据。

优化建议
  1. 看 OutSideViewArmyLineMgr 的实现，确认行军线数量是否可裁剪——视野外的行军线不计算 vertex
  2. CalculateVertexJob 是 Burst 并行计算，已用 Job 系统，优化空间在减少输入量而非并行度
