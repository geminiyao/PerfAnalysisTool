§0 结论先行：三条主线讲清这次退化

按对帧率贡献排序，三条独立结论。每条配 ASCII 图 + 关键数字 + 详见 §X。

① 主线程瓶颈形态：从'几乎全程在算'退化成'半睡型'，Sleep 增量几乎全是等 GPU 严重

> 🔴 throttle 态主线程有近四成时间在 Sleeping，其中绝大多数是在等 GPU 完成渲染——单次等 17.8ms 已经超过一个 60Hz vsync 周期（16.66ms），说明 GPU 撑爆了 swapchain 排队。
>
> 关键数字：Gfx.WaitForPresent 单次 avg base 0.9ms → cur 5.8ms → throttle 17.8ms（cur→throttle 涨 ×2.7）；URP.AfterRendering 占比 cur 22.5% → throttle 41.36%。Sleep 增量几乎 100% 是等 GPU。详见 §3、§6。

② 业务侧稳态税：Core.Update 每帧雷打不动吃掉近四分之一的帧时 高

> 🟠 Core.Update 是 GPU 等待之外的第二成本：cur 每帧 7.32ms，占 PlayerLoop p50 的 24.1%。其中 LuaMgr 12.5%（Lua 业务调度层）、MapManager 9.5%（含行军线管理 5.19%）。这些不是尖峰而是每帧都跑的稳态税，决定帧率天花板。行军线是 cur→throttle 唯一涨幅显著的业务模块（×1.37）。
>
> 关键数字：Core.Update base 10.3%（空场景无业务）→ cur 24.1%；行军线 cur 1.575ms/帧 → throttle 涨 ×1.37。详见 §5。

③ 降频放大器：SoC 把大核压到 59% 让 GPU 更慢，是退化的第二推手 高

> 🟠 throttle 态 SoC 大核频率仅达理论上限的 59.2%（严重低频），中核 observed max 从 2419MHz 被压到 2227MHz（cpuinfo 上限始终 2419）——是 SoC 主动压频的间接证据。降频本身不直接卡帧，是让 GPU 更慢、放大第一条结论。
>

§3 主线程 off-CPU 归因：wait slice 重叠法 + 状态分布 + 因果链

throttle 态主线程 38.99% 时间在 off-CPU，其中 89.34% 是可中断睡眠（S 状态）——几乎全在等 GPU。用 wait slice 重叠法定位到 Gfx.WaitForPresentOnGfxThread 单次 17.8ms 是核心增量。

byState 分布：S 状态占 off-CPU 的 89.34%，D 仅 1.3% 排除 binder/锁 严重

throttle 主线程 off-CPU 归因：S（可中断睡眠）89.34% 是绝对大头，几乎全在等 GPU；D（不可中断睡眠，含 binder/IO/锁）仅 1.3%，排除 binder IPC 和锁等待；R+（被抢占）2.78%（base 0.42% → ×6.6），与降频期间大核频率不足、任务排队增多一致，是弱辅助信号。

wait slice 重叠法：Gfx.WaitForPresentOnGfxThread 单次 17.8ms 是核心增量 严重

微观层在 waitSlices 里找 GPU 等待 slice：Gfx.WaitForPresentOnGfxThread avg 17.799ms，单次已超 60Hz vsync 周期 16.66ms（强信号阈值），count=427 与 PlayerLoop 帧数一致（每帧都在等）。三态演化 base 0.905ms → cur 5.834ms → throttle 17.799ms，cur→throttle foldChange 2.697（涨 ×2.7）。URP.WaitForPresent（avg 3.564ms，count 2135）和 Semaphore.WaitForSignal（avg 17.782ms，count 427）是父子重叠，用已剥洋葱的 Gfx.WaitForPresentOnGfxThread self 值做微观强度判定。

§4 降频时序：per-CPU + 形态 + 判定矩阵
