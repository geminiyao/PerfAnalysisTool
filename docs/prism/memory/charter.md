# PRISM — 性能分析 Master Agent · 宪章（Charter）

> 本文件是 Prism 项目的**北极星**。任何一个开发分支、任何一次细节调试，都必须能回答
> 「我在服务哪条锚定 Feature？」。答不上来 = 跑偏，砍掉。
>
> 维护约定：树干（北极星 + 五条锚定 Feature）**永不漂移**；只有分支/叶子随开发演进。
> 每次回到用户面前，先报坐标：「当前在锚定 Feature #X 的第 Y 分支，上游是什么，为什么需要你拍板」。

---

## 名字的含义

**Prism（棱镜）**：一束原始 perf 数据进去，折射成一谱清晰、可回溯的 findings；
三源（Unity / simpleperf / perfetto）折射进同一个分析引擎。

---

## 北极星（一句话）

> **造一个越用越懂这款游戏的性能分析师——它自己找问题、查数据验证、锚着源码给建议，
> 每个断言都可回溯，且用得越久越准、越会查、越懂业务。**

它不是"训练一个模型"，是"训练一个系统"：底层推理引擎用最强的现成模型（不动、不微调），
进化的是它周围的**知识、工具、质量基线**——改文件即生效，可解释、可 review、可回滚、可 git 管理。

## 五条锚定 Feature（树干 · 不可漂移）

### F1. 分析师，不是作文机
每一个断言都回溯到一次**可复现、带 provenance（runId + query）的查询**。零编造。
这是灵魂：把 LLM 从"在固定 digest 上写作文"变成"提假设、去数据里验证的分析师"。
反直觉但成立——**能查了就不用猜，幻觉反而下降**。

### F2. 自由发现
热点从**整棵数据**里自然浮现，不靠预设盯防名单（watch-spec 白名单已废弃）。
报告结构**跟着 findings 走**（N 个 finding → N 个 section），不套死 §0–§9 模板。
watch-spec 的 deviceTiers / ruleTemplates / contextClassifiers **不废，但改用途**：
从"输入端过滤器（看哪里）"挪到"输出端评判器（看到之后算多严重、按什么维度切）"。

### F3. 组合，不重推
单源产出**唯一权威**的结构化 findings；diff = 两次 run 的 findings + delta 的函数；
cross = 三源 findings 的**融合函数（引用/链接，不复述）**。
综合报告只讲那**非冗余的 20%**：off-CPU wait 归因、热节流因果链、native↔managed 对账，
外加"交叉验证结论"一行（把 confidence 从单源孤证抬到三源交叉验证），**不重贴三棵调用树**。

### F4. 三条进化回路（"自我进化"的全部含义）
- **知识回路**（越用越懂游戏）：确认的业务归因沉淀进知识库（aoe-cpu-knowledge 从静态文档变长期记忆）。
- **能力回路**（越用越会查）：Provider 自举——LLM 查不到的数据产出 `DataRequest`；
  高频复现的缺口固化成新查询工具 / provider 字段。分析层反向驱动数据层。
- **质量回路**（越用越准）：金标集 + 日常"真/假"确认。可回归、可量化召回/误报，敢放开自由度。

### F5. 源码锚定的建议
只有当某 finding 的证据**指向某符号、且源码已被检索出来**，才准对该段代码发言。
无 perf finding 指向的符号 + 未检索的源码 = **不许给代码建议**。
优化建议本身是带 confidence 的 finding，同样过 quality gate。

### F6. TL;DR 优先（第一屏定生死）
每份报告/结论开头必须有**傻瓜式醒目摘要**：一句话结论 + 根因 + 建议 + 置信度 + 颜色分级（🔴🟡🟢），
从真实最高优先级 findings **升顶**，不是营销话术。第一屏看不懂"关我什么事、我该干嘛" = 产品失败。
（只有"分析师"给得出这种摘要；"作文机"只会给"MeshUI 很热建议优化"这类正确的废话。）

### F7. 单源榨干、多源增益（降级不降智）
每一源**独立在场**时都必须产出该源**能力上限**的分析：
- 单 Unity：榨 timeline 里的**线程等待因果**（主线程在 wait 时是被 render thread 还是 job worker 挡住——
  信息在 timeline 里，只是要功力去读、去对齐、去推）、周期性尖峰、条件相关性。
- 单 simpleperf：榨稳态 native 热点、层次归因（business/engine/runtime/middleware）。
- 单 perfetto：榨 off-CPU / sched / 热节流因果。

多源在场是**叠加增益 + 交叉验证**，而非前置依赖。**能力随数据源数量优雅升级，绝不"缺一源就废"。**
（架构兑现：核心探索内核**源无关**，只认识"有哪些工具可用"；加一源 = 注册该源工具集，内核代码不改。）

### F8. 动态判定，非套路清单
每次分析先对照**约定性能指标 + baseline** 给出**总体判定**（优秀/及格/偏弱/不合格 + 坏在哪 + 坏多少 + 较上版趋势）。
**数据好就明确说好**——一个只会报问题、从不说"你这次没问题"的系统没有判断力，只有找茬本能，不可信。
报告是"这次到底行不行"的**判断**，不是"永远有这问题那问题"的**清单生成器**。
（F8 + F6 合体：报告第一屏 = Verdict「这次行不行」+ TL;DR「最该看的几条」。）

> "全自动进化 Agent" = F1–F8 全部长成后的**涌现结果**，是长期目标，不是某一期任务。

## 架构第一原则：弹性、可插拔、源无关（不许再做死）

旧管线死在硬编码（固定 §0–§9、provider 字段写死、LLM_FILL 槽位写死）。Prism 的核心是
**"源无关的探索内核 + 可插拔的能力插件"**，不是一条写死的流水线。四个可插拔：
1. **工具可插拔**：查询工具注册进 registry，加工具 = 加文件 + 注册，不碰探索内核。
2. **源可插拔**（F7 的架构兑现）：内核不认识具体源，只认识可用工具集；加源 = 注册工具集，内核零改动。
3. **Finding 开放可扩展**：evidence 是通用结构（source + query + 数据），不给特定源写死字段。
4. **报告结构由 findings 驱动**（F2）：renderer 遍历 findings 生成 section，无固定模板。

## 建造顺序（给五棵树浇水的时间表）

- **阶段一 — 先证明"分析师"比"作文机"强**（服务 F1 F2 F6 F7 F8）
  锁死 **unity single 最小切片**，靶子 = **"单 Unity 榨干"**：用同一份 Unity 数据，挖出线程等待因果 /
  周期性尖峰 / 条件相关性等"用 profiler 一眼看不出、要功力才挖得到"的深层结论。
  3~4 个只读查询工具 + Phase A 自由探索出 findings + 沿用旧 renderer。
  挖 3~5 个历史案例当金标，验证 Prism 能捞出旧管线/人肉 profiler 漏掉的问题。**只有这步成立，后面才有意义。**
- **阶段二 — 接反馈，让它开始进化**（服务 F4）
  finding 人工确认（质量回路）+ DataRequest 记录（能力回路）+ 确认归因沉淀进知识库（知识回路）。
- **阶段三 — 放开 + 扩展**（服务 F3 F5）
  推广到 diff/cross、接源码符号锚定、让三条回路自动转。

每一步都能独立产出价值，随时可停可回退。**不是赌一个大爆炸，是滚一个越滚越大的雪球。**

## 关键既定共识（防止重新拉锯）

- watch-spec 白名单 = 枷锁，已废；deviceTiers/ruleTemplates/contextClassifiers 保留但改为"评判器/打标维度"。
- **Unity profiler 无"系统性盲区"**（修正早期误判）：timeline view **能**看出主线程 wait 时是被 render thread
  还是 job worker 挡住——线程等待关系是可见的，只是要功力去 timeline 里读/对齐/推。perfetto 的优势不是
  "能不能看见"，而是 off-CPU 给了**开箱即用的归因标签**（wait on GPU/lock/vsync/GC），提炼所需功力更低。
  这一修正反而强化 F7：单 Unity 下 Prism 的价值 = 当那个"有功力、有耐心、会读 timeline"的分析师。
- 确定性回放**非必需**：采同一经典场景即可；环境变量（敌人数/网络/RNG）是性能的自变量而非纯噪声，
  能把"变慢"正确归因到"敌人多了"恰恰证明分析能力强。想断言"代码 regression"时，用"同版本多跑取中位数+看方差+LLM 查 context"排除环境因素，不需回放。
- 三源重叠信息（如主线程热点调用树）**要交叉 check**，但产物是"一行带置信度的对账结论"，不是三棵重复的树。
- 金标集**不靠脑补穷举**：主力来源是历史已修 bug 回灌（采集现成、答案现成）；日常"真/假"确认让它随用随长。
  金标集不约束 LLM 能力，也不进生产路径——它是给用户的"体温计"（量召回/误报），不是给 LLM 的"笼子"。
