§0 结论先行：三重压力叠加，throttle 态从 33fps 跌到 21fps

按对帧率退化贡献排序的三条独立结论，每条配 ASCII 图 + 关键数字 + 详见 §X 引用。

① GPU 撑爆：主线程从'几乎全程在算'到'半睡型'，Sleep 增量核心是等 GPU 严重

throttle 态主线程 38.99% 时间在 Sleeping，其中 Gfx.WaitForPresentOnGfxThread 单次 avg 17.8ms 已超过 60Hz vsync 周期 16.66ms——说明 GPU 一帧渲染时间超预算，swapchain 排队撑爆。三态演化：base 0.9ms → cur 5.8ms → throttle 17.8ms，cur→throttle foldChange ×2.7。详见 §3。

② SoC 降频：大核频率被压到 59%，中核 max-freq 也被压到 2227MHz 高

bigCoreReach 三态 74.9% → 75.6% → 59.2%，throttle 跌破 65% 严重低频线。中核 cpu4-6 observed max 从 2419/2342 降到 2227MHz（cpuinfo 上限始终 2419MHz），是 SoC 主动压低 max-freq 的间接证据。降频加剧 GPU 等待（频率被压 → GPU 更慢 → 主线程等更久）。详见 §4。

③ 业务脚本 Core.Update 稳态占 24%：LuaMgr + MapManager 是大头 高

cur 态 Core.Update 每帧 7.32ms，占 PlayerLoop p50 的 24.11%（远超 5% 红线）。其中 LuaMgr 12.51%（Lua 业务调度层，含 BattleHeadMgr 4.92% + MapSignificanceMgr 3.99%）、MapManager 9.54%（含 OutSideViewArmyLineMgr 5.19%，cur→throttle 涨 ×1.37）。每帧都在跑，是稳态成本不是尖峰。详见 §5。

§3 主线程 off-CPU 归因：wait slice 重叠法锁定 GPU 等待

throttle 态主线程 38.99% 时间在 Sleeping，用 wait slice 重叠法（v5.3 §4.3）锁定 Sleeping 的归因：byState.S 占 off-CPU 89.34%（宏观层），Gfx.WaitForPresentOnGfxThread 单次 17.8ms（微观层强度）。排除 binder/锁/IO 阻塞（D 仅 1.3%）。

byState 分布 + wait slice 重叠：Sleeping 的 89% 是等 GPU 严重

throttle 态主线程 byState 分布：S（可中断睡眠）占 off-CPU 89.34%、D（不可中断睡眠，含 binder/IO/锁）仅 1.3%、R（running）6.58%、R+（被抢占）2.78%。S 状态占绝对主导，说明主线程主要在'等'而非'被阻塞'。在 waitSlices 里找 GPU 等待 slice：Gfx.WaitForPresentOnGfxThread avg=17.799ms（超 vsync 16.66ms），count=427 与 PlayerLoop 帧数一致（每帧都在等）。三态演化 base 0.905ms → cur 5.834ms → throttle 17.799ms，cur→throttle foldChange ×2.7。排除项：D 1.3% 排除 binder IPC 和锁等待；R+ 从 0.42% 涨到 2.78%（×6.6）与降频期间大核频率不足有关但占比小。

§4 降频时序：大核 59% 严重低频 + 中核 max-freq 被压

三态降频形态：base/cur bigCoreReach 74-76%（弱信号，负载-频率背离但未严重），throttle 跌到 59.2%（严重低频）。中核 cpu4-6 observed max 从 2419/2342 降到 2227MHz（cpuinfo 上限始终 2419MHz），是 SoC 主动压低 max-freq 的间接证据。无 thermal sidecar，无法用温度 Δ 做第二信号确认，定 likely 档。

降频判定矩阵：likely 档（缺温度确认） 高

降频矩阵多信号同向：(1) bigCoreReach 三态 74.9%→75.6%→59.2%，throttle 跌破 65% 严重低频线；(2) 中核 cpu4-6 observed max 三态 2419→2342→2227MHz，cpuinfo 上限始终 2419MHz，observed max 低于 cpuinfo max 是 SoC 主动压频的间接证据；(3) big 核 cpu7 reachPct 三态 73.7%→77%→61.4%，throttle 跌幅最大；(4) R+ 被抢占从 0.42% 涨到 2.78%（×6.6），与降频期间大核频率不足、任务排队增多一致。温度信号缺失是硬伤，无法用'温度 Δ≥5°C 或采后≥75°C'做第二信号确认，综合定 likely 档。

§7 ROI 优化方向：按 severity + 贡献排序

优化方向按'对帧率退化贡献'排序：P0 是 GPU 负载（throttle 第一主因），P1 是降频（第二主因，治本靠降负载），P2 是业务脚本稳态税（第二成本），P3 是 GC 预防（罕见尖峰）。

P0：降低 GPU 负载（throttle 第一主因） 严重

throttle 态单次 Gfx.WaitForPresent 17.8ms 远超 vsync 16.66ms，说明 GPU 一帧渲染时间已超 16.67ms 预算。需降低 GPU 负载。URP.AfterRendering 占 41% 是渲染等待集中点，但该节点是叶子（无子 marker），需要看 URP AfterRendering 的具体 Pass 配置才能给更细建议——是 PostProcessing、Blit 还是 FinalBlit 在贵。base 态 URP.Render 已占 36% 但 GPU 跟得上（wait 仅 0.9ms），说明渲染负载本身就不轻，cur/throttle 场景加了战斗/行军实体后 GPU 负载溢出。

降频是 SoC 热保护行为，根因是持续高负载导致温度累积。降低整体 CPU/GPU 负载是治本——见 P0 和 P2 的优化方向，把帧时压回预算内温度就不会触发降频。中核 max-freq 被压到 2227MHz（cpuinfo 2419MHz）说明 SoC 热管理已介入中核集群，不只大核——优化时不能只盯大核负载，中核集群的 ECS/Job 调度也要均衡。
