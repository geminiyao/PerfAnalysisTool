§0 结论先行：三条独立结论按强度排序

throttle 态从 33fps 跌到 21fps 不是单一元凶，是 GPU 撑爆 + 降频加剧 + 业务稳态税三者叠加。下面三条结论按对帧率的贡献排序，每条配 ASCII 图 + 关键数字 + 详见 §X。

① GPU 撑爆：主线程近 4 成时间在等 GPU，单次等 17.8ms 超过一个 vsync 周期 严重

throttle 态主线程有 38.99% 的时间在 Sleeping，其中绝大多数是在等 GPU 完成渲染。单次 Gfx.WaitForPresentOnGfxThread 平均等 17.8ms，已经超过一个 60Hz vsync 周期（16.66ms）——意味着 GPU 一帧渲染时间已超预算，swapchain 排队撑爆。这是 throttle 态从 33fps 进一步跌到 21fps 的第一主因。

② SoC 降频：大核频率被压到 59%，中核 max-freq 被压到 2227MHz 高

throttle 态 SoC 大核频率仅达理论上限的 59.2%（严重低频），中核 cpu4-6 的观测 max 频率从 cur 的 2342MHz 降到 2227MHz（低于 cpuinfo 上限 2419MHz），是 SoC 主动压低 max-freq 的间接证据。降频让 GPU 更慢，是 GPU 等待的第二放大器。

§3 主线程 off-CPU 归因：wait slice 重叠法 + 因果链

throttle 态主线程 Sleeping 38.99%，用 byState 分布 + wait slice 重叠法定位'等的是什么'。结论：89.34% 的 off-CPU 时间是 S 状态（可中断睡眠），其中绝大多数是 Gfx.WaitForPresent——等 GPU。

byState 分布 + wait slice 重叠法 严重

throttle 态主线程 byState 分布：S 状态占 off-CPU 的 89.34%（宏观归因），D 状态（不可中断睡眠，含 binder/IO/锁）仅 1.3%——排除 binder IPC 和锁阻塞。微观层在 waitSlices 里找 GPU 等待 slice：Gfx.WaitForPresentOnGfxThread avg=17.799ms、count=427（与 PlayerLoop 帧数一致，每帧都在等），URP.WaitForPresent avg=3.564ms、count=2135。三态演化：base avg 0.905ms → cur 5.834ms → throttle 17.799ms，cur→throttle foldChange=2.697（涨 ×2.7）。

§7 ROI 优化方向：按 severity + 贡献排序

P0：降低 GPU 负载（throttle 强 GPU-bound，第一主因） 严重

优化建议
