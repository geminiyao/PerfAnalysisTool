§7 ROI 优化方向
P0 · 降低 GPU 负载严重
throttle 单次 wait 17.8ms 远超 vsync，GPU 一帧渲染超 16.67ms 预算。检查 DrawCall/Shader/overdraw，URP.AfterRendering 占 41% 是渲染等待集中点，需看具体 Pass 配置。
优化建议
  1. 检查 DrawCall 数量、Shader 复杂度、overdraw，定位 GPU 负载溢出源
  2. URP.AfterRendering 占 41%——看具体 Pass（PostProcessing/Blit/FinalBlit）哪个在贵
  3. 渲染分辨率降档评估（900p → 720p），base 已占 36% 说明负载本就不轻
  4. 补 GPU busy/freq counter 采集，把 GPU 满载判定从间接强信号升到 confirmed
P0 · 行军线 OutSideViewArmyLineMgr高
cur→throttle 唯一涨幅显著的业务模块（×1.37）。CalculateVertexJob count=57820——顶点计算是子任务之一。叶子无子 marker，需加更细的 Profiler marker。
优化建议
  1. 给 OutSideViewArmyLineMgr 加更细 marker（顶点计算/线段更新/渲染提交分开）
  2. 评估 count=57820 是否过高——是否每帧全量重算，可改脏标记增量
  3. 看 OnUpdate 实现，判断是顶点计算、线段更新还是渲染提交在贵
P1 · LuaMgr 子业务 marker 细化高
LuaMgr 12.51% 是 Core.Update 下第一大头。MapSignificanceMgr 每帧 4.9 次 MapObjRefresh——刷新频率可评估。BattleHeadMgr 的 Init/LoadUI（316 次）需确认是否重复初始化。
优化建议
  1. 给 OutSideViewArmyLineMgr/BattleUIManager 加更细 marker（目前是叶子无法拆分）
  2. MapSignificanceMgr 每帧 4.9 次 MapObjRefresh——评估是否过高，可改事件驱动
  3. BattleHeadMgr 的 Init/LoadUI（316 次）——确认是否在战斗中重复初始化
P1 · 降频治本 = 降负载高
降频是 SoC 热保护行为，根因是持续高负载。治本是降整体 CPU/GPU 负载，把帧时压回预算内温度就不会触发降频。中核 max-freq 也被压，优化时不能只盯大核。
优化建议
  1. 降整体 CPU/GPU 负载是治本——见 P0 GPU + P0 行军线
  2. 中核集群 max-freq 也被压——ECS/Job 调度也要均衡
  3. 下次采集补 thermal sidecar + scaling_max_freq（需 root），升到 confirmed
P2 · GC 预防中
GC 不是当前主瓶颈，但 throttle 单次 GC.Collect 32.9ms 是实打实卡顿尖峰。MeshUIManager 61 次/帧、TimeText.7 24 次/帧可排查。
优化建议
  1. MeshUIManager/TimeText 排查是否有不必要的每帧字符串拼接/临时 List
  2. GC.Collect throttle 单次 32.9ms——设置 GC.latencyMode=LowLatency
  3. 渲染层分配（URP.BeforeRendering/Inl_OpaquePass）是引擎内部，升级 Unity 或调 URP 配置
P2 · 下次采集补三类盲区信息
本次 trace 无 ECS Worker、无 LuaMtGC、无 RHI Thread——非典型 Unity 采集。
建议补采
  1. 补 ECS Worker 线程——确认 Job 是否在主线程同步执行
  2. 补 LuaMtGC marker——AOE3D 用 xLua，Lua GC 可能是隐藏卡顿源
  3. 补 RHI Thread——区分 Render 命令录制和 RHI driver 调用
