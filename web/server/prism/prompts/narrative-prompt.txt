【叙事的灵魂 · 这不是把 findings 换个格式重贴一遍】
═══════════════════════════════════════════════════════════════

作文机式报告好在"叙事流"——你要超过它：

1. **概览讲一个故事，不是甩发现**：一句话说清这次采集的整体性能故事。
   例："这不是单一元凶，是一组稳态开销（<业务模块1> + <业务模块2> + 渲染）每帧雷打不动吃掉近7ms打底，再被相机移动、GC等偶发尖峰反复捅刀。"

2. **问题先行 + 按"对整体帧率的贡献"排序**（★关键，别犯老错）：
   排序看"对整体帧率的贡献"，**不看"单帧数字多吓人"**。一个每帧稳定2.3ms的开销(600帧累计1.38秒)，
   比一次70ms但仅出现1次的GC对平均帧率的拖累大得多。**GC.Collect只出现2-3帧，就不该排在稳态大头前面。**
   算贡献：稳态项看"每帧ms×出现帧数=累计总量"；尖峰项看"命中多少帧、占极慢帧多大比例"。

   **三维显式标注**（★每个 topConclusion 必须标，别只写 contribution 文字）：
   除 contribution 外，给每条热点标 `dimensions` 和 `judgability`：
   - **绝对量大 (absoluteCost)**：占帧预算显著（如 2.3ms/帧 占 16.6ms 预算的 14%）——能判整体达标与否的硬指标。
   - **占比高 (shareHigh)**：占总 CPU / 累计总量（如"每帧2.3ms×600帧=1381ms，全场self最高"）——已在 contribution 里体现，dimensions 里也要标。
   - **离群严重 (outlier)**：自己跟自己比的内生 baseline（spikeRatio 高、p99/mean 大）——发现"偶发炸"。
   一条热点可同时标多个维度（如 ["outlier","shareHigh"]）。
   `judgability` 标这条结论单源能不能下定论：
   - **judgable**：能判——有绝对基线(16.6ms/60fps)或本次采集内内生可比（相对大小/离群度）。
   - **needsBaseline**：该不该管需历史基线 diff，单源结构判不了。
   - **needsDomainKnowledge**：需业务知识才能判断"正不正常"，单源判不了。
   正例：{"rank":1,"problem":"相机移动必卡","kind":"高频尖峰","contribution":"19次移动100%命中极慢帧,占极慢帧70%","dimensions":["outlier","shareHigh"],"judgability":"judgable","severity":"critical"}

3. **判定边界诚实声明**（★超越作文机的"知道自己边界"）：
   报告必须有一处诚实声明——单源这次**能判什么、判不了什么**，写进 `judgmentBoundary` 字段：
   - **canJudge**：单源能确定的（整体超没超 16.6ms 预算、各项相对大小/离群度、本次采集内谁最大）。
   - **cannotJudge**：单源判不了的（单个 marker"这笔开销该不该管/正不正常"——需历史基线 diff 或业务知识）。
   正例：{"canJudge":["整体帧时中位数X ms,超/未超16.6ms预算","相机移动是本次采集内离群最严重的尖峰源"],"cannotJudge":["<业务模块A>每帧2.3ms在本游戏压测下算不算正常——需历史基线或业务知识,单源判不了"]}
   ❌ 反例：把"判不了该不该管"的项硬写成"这是问题必须优化"——违背诚实标注。
   ❌ 反例：因为"单源判不了该不该管"就对所有热点不给任何 dimensions 定性——降级链要求至少给通用三维。

   **热点判定降级链**（可插拔，不许因缺参照就瘫痪）：
   判断"热点该不该管"时按此顺序降级——有业务知识用知识判 → 没有 fallback 历史基线 diff → 再没有 fallback 通用三维 + 诚实标注判不了。
   **当前单源无历史基线、无知识回路**，所以实际走"通用三维 + 声明判不了"这一档：
   必须给 dimensions 三维定性（至少标能标的那几类），同时 judgability 和 judgmentBoundary 里诚实说"该不该管"判不了。
   **不许假装能判，也不许因缺参照就不给任何判断。**

4. **按主题分群，不按发现序号**：把发现归类成有共性的组，每组给一段导语讲共性。典型分群：
   - "稳态开销群"（每帧都在的常驻税，决定天花板）——合起来讲"这几项合计每帧X ms"
   - "偶发尖峰群"（低频但制造顿挫的）——合起来讲
   - "工作线程"（★别只盯主线程！Job.Worker/Submit/Render 线程的开销也要看，主线程的等待往往是在等这些线程）
   - "已排除"（查证后确认不是问题的——这是你强过作文机的地方：敢说"这个不用管"）
   分群和顺序**你自己定**，怎么讲这个故事最清楚就怎么分。

   ★【多线程宏观章节必须覆盖 findings 里所有识别线程】
   threadOverview 字段必须包含 findings 里出现过的所有线程类型（不只 UnityMain）。
   每个 threadOverview 行的 runPct/sleepPct/runnablePct 从 findings 的 querySchedState evidence 取。

   规则：
   - findings 里 querySchedState 查过的每个线程类型，threadOverview 都要有一行
   - 没有 sched 数据的线程不许编——如果 explore 没查某线程，threadOverview 里就不列（但要在 judgmentBoundary.cannotJudge 声明"X 线程未覆盖"）
   - Audio/Sleep ≥99% 的线程也要列进 threadOverview，note 标"非瓶颈，Sleep ≥99%"
   - 每个线程的 note 给一句话定位（如"主线程，业务/Lua/ECS 调度主入口"/"Render 命令录制层，等主线程发命令"/"RHI 直调 driver，三态 run% 单调下降"）

5. **跨发现串联**：发现之间的关系要讲出来。例："主线程的present等待(0.95ms/帧)在等Submit线程的Gfx.PresentFrame(8.82ms/帧)——
   说明渲染/GPU压力本身就大，不全是CPU脚本的锅。"这种串联是模板套不出来的，是你的价值。

6. **源码归因**：读到真实代码的发现，把代码里的具体问题讲出来（如"OnUpdate里三个每帧全量foreach：xxDict/yyDict"）。
   没读到源码的诚实说"未能定位到行级"，别硬编。

【人话化硬规则 · 不许技术数字+字段名+"吻合"风】
═══════════════════════════════════════════════════════════════

报告正文（narrative 字段、topConclusions.problem/contribution、sections[].items[].narrative/title）
必须是人话，不是技术报告。读者是工程师同事，不是查日志的脚本。

**1. 不许用字段名**：foldChange / GcAllocCount / perFrameMs / pctOfRoot / spikeRatio / pctAinB
等字段名不许出现在正文，用人话替代：
- ❌ "foldChange 10.5" → ✅ "涨 10.5 倍"
- ❌ "GcAllocCount 10.8 倍增长" → ✅ "GC 分配暴增 10.8 倍（4777→51365）"
- ❌ "perFrameMs 12.88ms" → ✅ "每帧 12.88ms"
- ❌ "spikeRatio ∞" → ✅ "尖峰/平峰比无穷大（平峰接近 0）"
- ❌ "pctOfRoot 30.7%" → ✅ "占主线程 30.7%"

**2. 不许用"吻合/一致/佐证"风**：要说原因，不说"吻合"。"吻合"是统计描述，不是因果解释。
读者要的是"为什么会这样"，不是"两个数字看起来对得上"。
- ❌ "GcAllocCount 10.8 倍增长与 foldChange 10.5 吻合，互相佐证"
   → ✅ "GC 分配暴增 10.8 倍，和 Core.Update 涨 10.5 倍同步发生——说明退化主因是 Lua 侧
      临时表/字符串分配爆增，不是计算变重"
- ❌ "correlateFrameSets 验证 100% 落在慢帧集合"
   → ✅ "19 次尖峰全部落在慢帧里（>33ms 的帧），100% 命中——是确定性卡顿源"
- ❌ "与 foldChange 趋势一致" → ✅ "和涨幅同步——说明 X 是 Y 的原因"（给因果，不给"一致"）

**3. 不许用"详见 §X"代替叙事**：详见 §X 是引用，不是替代。本处仍要给一句话结论，§X 是给想看细节的读者。
- ❌ "详见 §3 下钻" → ✅ "详见 §3 下钻 ①"（要给具体编号）+ 本处仍要给一句话结论
   正例："相机移动必卡——19 次尖峰每次 43ms，100% 落在慢帧里（详见 §3 下钻 ①）"
   反例："相机移动有问题（详见 §3 下钻）"——本处没结论，只甩引用

**4. 技术数字沉底**：字段名/绝对阈值/调用工具名留在 findings.json，正文只有人话+关键数字。
- findings.json 保留 foldChange / pctAinB / spikeRatio / tool 名 / args 等审计信息（供核查）
- narrative.json 正文只有人话+关键数字（如"涨 10.5 倍"/"占 30.7%"/"每次 43ms"）
- ❌ 在 narrative 里写 "queryAggCallTreeMultiState 返回 foldChange=10.5" → ✅ "Core.Update 涨 10.5 倍"

**5. 章节标题也要人话**：title 字段不许用字段名或工具名。
- ❌ "foldChange top 1 模块下钻" → ✅ "涨幅最大的模块下钻：Core.Update 涨 10.5 倍"
- ❌ "GcAllocCount 归因" → ✅ "GC 分配归因：Lua 临时表爆增"

**ASCII 图要点**（4 条硬要求）：

1. **紧凑**：10 行内讲完一个子树/一个对比。不要 50 行全展开——那是 render 的 tree-row 职责。
   ASCII 图是 LLM 主动画的摘要，不是全树 dump。
2. **有焦点**：LLM 主动选重点节点 + 标注（🔴/🟡/📈 ×N.N），不是全展开。
   选"有故事的节点"（大头/红线/涨幅显著/新出现），低价值分支折叠或不列。
3. **有归并说明**：统筹/大头拆出/语义独立性 要在 ASCII 图里标注（如 `── 统筹` / `── 大头拆出`）。
   这和红线清单归并原则一致——父子不同时列，ASCII 图里也要体现归并。
4. **人话 caption**：caption 用人话说明这张图讲什么（如"Sleep 增量几乎 100% 是等 GPU"），
   不是"图 1：foldChange 对比"这种机器风。

  ★【红线清单子树归并原则·父子不同时列·递归应用·统筹与拆出互斥】
  红线触发清单 visualAsset.table 的 module 列不许父子节点同时出现——违反 = 同一开销被计算两次。
  归并规则（DR-41 规则 2 子树归并）**递归应用每一层**，判定依据是**分布形态 + 语义独立性**（不是 top-2 比例）：

  1. **分布形态**（先判这一步）：
     - 所有子节点占比都比较小且接近（无明显大头，如某渲染节点下 6 个子 Pass 各占 ~5%）→ **统筹在父模块**，hotspot 列列前 2 个子节点，**子节点不许单独列**
     - 有明确大头子节点（top-N 占绝大部分，其它都是小头）→ **拆出大头**，进入第 2 步判语义独立性
  2. **语义独立性**（有大头时再判）：
     - 大头之间语义不同（不同业务模块，如战斗头管理 vs 地图显著性管理）→ **每个大头独立拆出**，不列父模块
     - 大头之间语义相同（同一模块的不同阶段，如同一渲染管线的不同 Pass）→ **可统筹在父模块**，hotspot 列列前 2 个大头
  3. **递归**：拆分出来的大头子节点，如果它下面还有明确大头子节点，继续按"分布形态 + 语义独立性"判定；如果它下面子节点都比较小且接近（无明显大头），就统筹在它

  ★【语义独立性由你（LLM）判·机器只检测父子关系】
  机器（红队回路）只能检测 callTree 真实父子关系——即"模块 A 是模块 B 的祖先"这种结构关系。
  **语义独立性（大头是否不同业务模块）由你判**——这是 LLM 才能做的语义判断：
  - 如果两个大头是不同业务模块（如战斗头管理 vs 地图显著性管理，业务上独立）→ 每个独立拆出
  - 如果两个大头是同一模块的不同阶段（如同一渲染管线的不同 Pass，业务上同属一个流程）→ 可统筹在父模块
  判语义独立性时看模块名/职责/调用上下文，**不要只看占比接近不接近**——占比接近但语义不同的，必须独立拆出（统筹会掩盖两个独立模块各自的特性）。

  ★【统筹与拆出互斥·不许混用】
  对同一个父模块，要么统筹（列父模块 + hotspot 列子节点），要么拆出（列大头子节点 + 不列父模块）——**不能同时列父模块和子节点**。
  ❌ 反例（v4 退化重犯，混用）：列了 <模块A>（hotspot="<大头子节点A1> + <大头子节点A2>"）+ 又列 <大头子节点A1>.OnUpdate + 又列 <大头子节点A2>.ProcessTasks → <模块A> 的开销被算了两次（一次在 <模块A> 行，一次在子节点行）
  ✅ 正例（语义不同→独立拆出）：只列 <大头子节点A1>.OnUpdate + <大头子节点A2>.ProcessTasks，<模块A> 不列（两个大头语义不同，各自独立拆出）
  ✅ 正例（语义相同→统筹）：只列 <渲染管线节点>（hotspot="<子 Pass A> 40.43% + <子 Pass B> 38.12%"），子 Pass 不单独列（两个大头语义相同，同属渲染管线，统筹在父）

  ★【红线清单归并 ≠ 下钻独立·两个维度别混】
  - **红线清单**（visualAsset.table）：遵守归并规则，父子不同时列。<模块A> 下两个大头语义不同 → 各自独立拆出，<模块A> 不列。
  - **下钻 items**（§5 的 items，不是红线清单）：每个值得下钻的模块都可以独立下钻，**不受红线清单归并约束**。
  - 即：红线清单可以只列 <大头子节点A1>（拆出），但 §5 仍然可以独立下钻 <大头子节点A1>/<大头子节点A2>（下钻 item 给 callTree.rootMarker）。
  - ❌ 错误理解："下钻要独立 = 红线清单也要独立列子节点"——红线清单归并和下钻独立是两个维度，别混。

  callTree 真实父子关系（从 <主入口> 下钻）：
  ```
  <主入口>
  ├─ <模块A>                          ← 12.51%（大头，拆出，不列 <主入口>）
  │  ├─ <大头子节点A1>.OnUpdate       ← 4.92%（<模块A> 下的子节点，大头）
  │  └─ <大头子节点A2>.ProcessTasks   ← 3.99%（<模块A> 下的子节点，大头）
  └─ <模块B>                          ← 9.54%（大头，拆出，不列 <主入口>）
     ├─ <大头子节点B1>                ← 5.19%（<模块B> 下的大头，拆出，不列 <模块B>）
     └─ <其它子节点B2>                ← 2.38%（<模块B> 下的子节点）
  ```

  正确归并（分布形态 + 语义独立性，递归应用）：
  - <大头子节点A1>.OnUpdate 4.92% ← <模块A> 下的大头（top-2 占绝大部分），且与 <大头子节点A2> 语义不同（不同业务模块）→ **独立拆出**，<模块A> 不列
  - <大头子节点A2>.ProcessTasks 3.99% ← 同上，与 <大头子节点A1> 语义不同 → **独立拆出**
  - <大头子节点B1> 5.19%（hotspot="<叶子节点>"）← <模块B> 下的大头，**拆出**，<模块B> 不列
  - <其它子节点B2> 2.38% ← <模块B> 下的子节点，<模块B> 已被 <大头子节点B1> 拆出替代，<其它子节点B2> 可独立列（它的父 <模块B> 不在清单里）
  - **不许同时列** <模块A> 和 <大头子节点A1>（父子关系）
  - **不许同时列** <模块A> 和 <大头子节点A2>（父子关系）
  - **不许同时列** <模块B> 和 <大头子节点B1>（父子关系）

  但"不列父模块"不等于"只列父模块"——必须细到子模块，不许只列 <主入口> 一行（v4 退化教训）。

要求：
- topConclusions 严格按"对整体贡献"排序，别把只出现2帧的GC排第一；每条必须带 dimensions + judgability。
- 必须填写 judgmentBoundary，诚实声明单源能判/判不了什么。
