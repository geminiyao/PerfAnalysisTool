§0 结论先行：三态退化故事 + 三条独立结论

这次采集的整体性能故事是一条因果链：压测持续 → SoC 热保护降频 → GPU 变慢 → 主线程等 GPU → fps 崩盘。业务脚本 Core.Update 是每帧常驻税决定天花板，GC 只是偶发尖峰。三条结论按强度排序，每条配 ASCII 图 + 关键数字 + 详见 §X。

① 主线程瓶颈形态演化：从 base 的'几乎全程在算'到 throttle 的'半睡型'——核心增量是等 GPU 严重

throttle 态主线程有 38.99% 的时间在 Sleeping，其中 89% 是等 GPU 完成渲染。单次 Gfx.WaitForPresentOnGfxThread 平均等 17.8ms，已经超过一个 60Hz vsync 周期（16.66ms），说明 GPU 一帧渲染时间已超预算，撑爆了 swapchain 排队。这是 throttle 态从 33fps 进一步跌到 21fps 的第一主因。

§2 多线程宏观：所有线程三态健康度 + 一句话定位

本次 trace 线程类型简单：UnityMain（主线程）、UnityGfxRenderS（渲染线程）、Audio 线程池 5 个子线程、AsyncWorker。主线程 Run 三态单调下降（86.94%→56.99%），Sleep 单调上升；渲染线程同步变闲（Run 25.98%→16.71%）；Audio 池和 AsyncWorker 全部 Sleep ≥94% 已排除。无 ECS Worker 线程、无独立 LuaMtGC 线程、无 RHI Thread。

多线程宏观 信息

主线程是唯一瓶颈线程：Run 三态单调下降 30 个百分点，Sleep 单调上升 27 个百分点，增量几乎全是等 GPU。渲染线程同步变闲（throttle 最闲 16.71%），印证 GPU 在拖而非 CPU 渲染命令录制在贵。Audio 线程池 5 个子线程 Sleep 全 ≥94%，AsyncWorker Sleep 99.88%，均非瓶颈。注意 base 采集窗口短（11.4s）只采集到 4 个线程（UnityMain/UnityGfxRenderS/AudioMixer/AudioStream），AAudio_1/AudioTrack/GVoiceRender/AsyncWorker 是 throttle 窗口长（19.9s）才采集到，是窗口差异不是状态差异。

§3 主线程 off-CPU 归因：wait slice 重叠法 + 状态分布 + 因果链

用 wait slice 重叠法定位主线程 Sleeping 的真实去向。throttle 态主线程 Sleeping 38.99%，byState 显示 S 状态占 off-CPU 的 89.34%（宏观归因）；微观层 Gfx.WaitForPresentOnGfxThread 单次 17.8ms × 427 帧 = 7590ms，是 Sleeping 的核心去向。D 状态（binder/IO/锁）仅 1.3%，排除外部阻塞。

byState 分布 + wait slice 重叠：Sleeping 的 89% 是等 GPU 严重

throttle 态主线程 off-CPU 时间里，S 状态（可中断睡眠）占 89.34%，D 状态（不可中断睡眠，含 binder/IO/锁）仅 1.3%，R+（被抢占）2.78%。S 状态占绝对主导说明主线程在等某个可唤醒的事件——微观层 wait slice 显示 Gfx.WaitForPresentOnGfxThread avg 17.8ms × 427 帧 = 7590ms，URP.WaitForPresent avg 3.56ms × 2135 帧 = 7608ms，两者 totalMs 接近且远超 sleepingMs（3346ms），是因为父子 slice 重叠（Gfx.WaitForPresentOnGfxThread ⊂ URP.WaitForPresent）。剥洋葱后用 byState.S 89.34% 做宏观归因，单次 avgMs 17.8ms 做微观强度判定。

§4 降频时序：per-CPU + 形态 + 判定矩阵

降频判定矩阵：likely 档（多信号同向，缺温度确认） 高

§7 ROI 优化方向：按 severity + 贡献排序

优化方向按 severity + 对整体帧率贡献排序。第一梯队是 GPU 负载（throttle 第一主因）+ 降频治本（降低整体负载让温度不触发降频）；第二梯队是业务脚本稳态大头（Core.Update 24%）；第三梯队是 GC 预防性优化（罕见尖峰但单次卡顿）。

P0：降低 GPU 负载——throttle 态第一主因，单次等 17.8ms 超 vsync 严重

throttle 态 GPU 一帧渲染时间已超 16.67ms 预算，需降低 GPU 负载。方向：检查 DrawCall 数量、Shader 复杂度、渲染分辨率（AOE3D 移动端默认 900p，可考虑降档）、overdraw。URP.AfterRendering 占 41% 是渲染等待集中点，需拆分 PostProcessing/Blit/FinalBlit 各自耗时。base 态 URP.Render 已占 36% 说明渲染负载本身不轻，cur/throttle 加战斗/行军实体后溢出。

优化建议
  1. 检查 DrawCall 数量——战斗/行军场景的部队模型、特效、行军线是否导致 DrawCall 暴涨
  2. 简化 Shader 复杂度——移动端 Shader 可降档
  3. 降低渲染分辨率——AOE3D 移动端默认 900p，可考虑降档到 720p
  4. 检查 overdraw——特效/行军线/部队模型的重叠渲染
  5. 拆分 URP.AfterRendering 的 Pass 配置，定位是 PostProcessing/Blit/FinalBlit 哪个在贵
P0：降频治本——降低整体 CPU/GPU 负载让温度不触发降频 高

降频是 SoC 热保护行为，根因是持续高负载导致温度累积。治本是降低整体负载（见 GPU + 脚本优化方向），把帧时压回预算内温度就不会触发降频。中核 max-freq 被压到 2227MHz 说明 SoC 热管理已介入中核集群，不只大核——优化时不能只盯大核负载，中核集群的 ECS/Job 调度也要均衡。如需确认降频，下次采集补 thermal_before/after.txt 和 scaling_max_freq（需 root）。

优化建议
