§0 结论先行：三态退化故事

三态从 base 的 60fps 一路退化到 throttle 的 21fps，是 GPU 满载 + 降频 + 稳态脚本税三者叠加的复合退化。按对整体帧率贡献排序：GPU 等待（第一主因）> 降频（加剧 GPU 等待）> Core.Update 稳态 24%（第二成本）> GC 尖峰（罕见但单次重）。

① GPU-bound：throttle 主线程 39% 时间在等 GPU 严重

throttle 态主线程有 38.99% 的时间在 Sleeping，其中绝大多数是在等 GPU 完成渲染。单次 Gfx.WaitForPresentOnGfxThread 平均等 17.8ms，已经超过一个 60Hz vsync 周期（16.66ms）——说明 GPU 一帧渲染时间已超预算，撑爆了 swapchain 排队。三态演化：base 0.9ms → cur 5.8ms → throttle 17.8ms，cur→throttle 涨 ×2.7。这是 throttle 态从 33fps 进一步跌到 21fps 的第一主因。

② SoC 降频：大核频率被压到 59% 高

throttle 态 SoC 大核频率仅达理论上限的 59.2%（严重低频，跌破 65% 红线），中核 cpu4-6 观测 max 频率从 cur 的 2342MHz 降到 2227MHz（低于 cpuinfo 上限 2419MHz）——是 SoC 主动压低 max-freq 的间接证据。三态 bigCoreReach 74.9%→75.6%→59.2% 单调下降，配合主线程 Sleeping 暴涨，构成 likely 档降频判定。降频是 SoC 热保护行为，根因是持续高负载导致温度累积，反过来又让 GPU 渲染更慢，形成负反馈。

③ Core.Update 稳态占 24%：业务脚本第二成本 高

cur 态 Core.Update 每帧平均 7.32ms、占 PlayerLoop 24.11%，是稳态业务成本大头。其中 LuaMgr（Lua 业务主入口）占 12.5%、MapManager 占 9.5%（含 OutSideViewArmyLineMgr 行军线管理 5.19%）。这些不是尖峰而是每帧都跑的持续成本，throttle 态因帧时拉长占比略降但绝对量仍在。base 是空场景无业务模块，cur/throttle 才进入战斗/行军压测场景，业务模块从无到有。

④ GC 尖峰罕见但单次重：throttle 单次 32.9ms 中

§3 主线程 off-CPU 归因：等 GPU 是 Sleep 增量的全部

用 wait slice 重叠法剥洋葱：throttle 主线程 Sleeping 38.99%，byState 显示 S 状态占 off-CPU 的 89.34%（宏观归因）。微观层在 waitSlices 里找 GPU 等待 slice——Gfx.WaitForPresentOnGfxThread avg 17.8ms，单次已超过 60Hz vsync 周期，count=427 与 PlayerLoop 帧数一致（每帧都在等）。

wait slice 重叠法：Sleep 增量几乎 100% 是等 GPU 严重

throttle 主线程 Sleeping totalMs 3345.7ms，其中 Gfx.WaitForPresentOnGfxThread totalMs 7600ms（count 427，avg 17.8ms）、URP.WaitForPresent totalMs 7608ms（count 2135，avg 3.56ms）、Semaphore.WaitForSignal totalMs 7592ms（count 427，avg 17.78ms）。注意 totalMs/sleepingMs 口径 >100%（691%）是因为 Gfx.WaitForPresentOnGfxThread ⊂ URP.WaitForPresent 父子重叠——用已剥洋葱的 byState.S pctOfOffCpu=89.34% 做宏观归因，单次 avgMs 做微观强度判定。
因果链：主线程发起渲染 → URP.Submit 提交命令 → 等 swapchain → GPU 完成 → 主线程被唤醒。throttle 态这个链条被 GPU 拖住，每帧等 17.8ms。
