# Unity 多态报告章节模板（DR-44 §3.2 第 2 层，对照 DR-43 多态方法论）

> 本模板定义 unity 多态报告的章节骨架，注入 narrative-prompt 的 {{REPORT_TEMPLATE}} 占位符。
> **和作文机的区别**：模板只定义章节结构 + 写作纪律，内容由 LLM 按 narrative-prompt 契约写。
> **不硬编码**业务名/绝对阈值/死模板（DR-41 + dev/conventions.md §六 + §6.1）。
>
> 多态适用场景：unity profiler 多样本对比（2 态 = 基线/当前，或 ≥3 态 = base/cur/throttle）。判定方法论对照 DR-43：用"相对倍数"（foldChange）+ "绝对增量"（防误判）+ "演化趋势"（单调性，≥3 态专属），不硬编码绝对 ms 阈值。
>
> **2 态和 ≥3 态通用本模板**：不区分 diff 还是 multi，统一叫多态。2 态是 N=2 的多态（基线/当前），≥3 态是 N≥3 的多态（base/cur/throttle）。表头写法兼容两种：2 态用"基线/当前"，≥3 态用"base/cur/throttle"。
>
> **unity 特有概念可保留**：PlayerLoop / URP / MonoBehaviour / UnityMain / UnityGfxRenderS / Job.Worker / GC.Alloc / GC.Collect 等 unity 引擎概念是数据源特定的，模板里可写。
> **AOE 专属业务名不许出现**：游戏专属业务名（如各类 Mgr / 业务模块名）用占位符 `<业务模块A>` / `<子模块A1>` / `<大头子模块B1>` / `<等待 slice>` / `<线程名>` 等，不写死在模板里。
> **perfetto 特有概念不许出现**：unity 没有 CPU 频率/温度/Android 帧时间线/Android 音频线程池等概念——不写降频章节、不写大核 reach、不写音频线程。

## 章节职责分工 · 防重复 · 每个 finding 只在一个地方详细展开

★【主战场原则·同一 finding 不许在多个章节重复详细展开】
同一个 finding 在报告里只能有一个"主战场"（详细展开的地方），其它章节只引用（一句话结论 + "详见 §X 下钻 ①"）。
违反 = 同一内容在 4 个地方重复展开（topConclusions / §0 / §3 红线清单 / §3 下钻 都写完整 callTree 子树描述），读者读到第三遍就烦了。

各章节职责（严格分工）：

| 章节 | 职责 | 不许做的事 |
|---|---|---|
| **topConclusions** | 结构化表格（problem/kind/contribution/dimensions/judgability/severity） | 不写 callTree 子树描述（├─/└─ 缩进树是 §3 下钻的职责） |
| **§0 全量结论叙事展开** | 人话叙事 + ASCII 图 + 关键数字 + "详见 §3 下钻 ①" | **不写 callTree 子树描述**（callTree 子树是 §3 下钻的职责）；§0 的 ASCII 图用三态/二态柱状图/因果链/演化对照，**不许用 ├─/└─ 缩进树** |
| **§3 红线清单** | 只给表格（模块/基线 ms/当前 ms/foldChange/占 p50%/红线类型/子函数热点），narrative 一句话定位 | **不详细展开**（不写 GC 归因/优化建议/源码归因，那是 §3 下钻的职责） |
| **§3 下钻** | 才是详细展开的地方（callTree 子树 + 红线判定 + GC 归因 + 源码归因 + 优化建议） | 不许重复 §0 的演化叙事（§0 讲"从基线到当前涨了多少"，§3 下钻讲"具体哪个子函数贵、为什么、怎么治"） |

**例：OnCameraMove finding 的正确分工**（占位符示意，不硬编码业务名）：
- topConclusions #1：表格行，problem="<相机移动模块>必卡：19 次尖峰 100% 命中慢帧"，contribution="19次×43ms,占极慢帧70%"
- §0 ①：人话"<相机移动模块>必卡——19 次尖峰每次 43ms，100% 落在慢帧里" + ASCII 图（三态柱状图或尖峰时序图）+ "详见 §3 下钻 ①"
- §3 红线清单：表格行，<相机移动模块> 0→43.14ms ×∞ 95.4% 新出现+占 p50≥5%
- §3 下钻 ①：详细展开（callTree 子树 frame 144 hotPath + 红线判定 + GC 归因 + 源码归因 + 优化建议）

**不许**：
- ❌ §0 和 §3 下钻都写完整 callTree 子树描述（├─/└─ 缩进 + 每个节点的 ms/占比）——那是重复
- ❌ §3 红线清单和 §3 下钻都详细展开（红线清单只给表格，下钻才详细）
- ❌ topConclusions 的 problem 文本和 §0 ① 的 title 高度相似（那是 topConclusions 复述，违反 §0 与 topConclusions 不重复规则）
- ❌ §0 ① 的 narrative 写"Core.Update 子树：├─ <大头子节点A1> 4.92% ├─ <大头子节点A2> 3.99%..."（完整 callTree 子树是 §3 下钻的职责，§0 只给 ASCII 摘要图 + 一句话结论 + 引用）
- ❌ §0 ① 的 narrative 写"下钻到 <大头子节点A1> 涨 57.88 倍（0.069→3.994ms），GC alloc 0→14043"（用任何形式讲子节点 ms/占比/foldChange/GC alloc，包括 narrative 文字/柱状图/因果链）——子节点细节是 §3 下钻的职责，§0 只给父模块"涨 X 倍 + 占 p50 Y%"级摘要
- ❌ §0 ① 的 narrative 写"核心增量来自 Lua 端：Core.Update→<Lua 入口模块>（涨 ×8.75）→...→<大头子节点A1>（涨 ×57.88，从 0.069ms 涨到 3.994ms）"——用因果链（→ 箭头）讲子节点名字 + 子节点 foldChange + 子节点 ms = 讲子节点细节 = 违规。LLM 易钻空子：认为"用 → 串起来的是因果链不是子节点"——错，因果链里的下游节点也是子节点。§0 只许讲父模块自身的 foldChange + 占 p50% + 绝对增量，下游子节点链全部放 §3 下钻
- ❌ §0 ② 的 narrative 写"frame 144 的 callTree 显示 <子模块> 在 LateUpdate 路径里炸了 56.4ms"——具体帧 + 子节点 ms = 讲子节点尖峰细节 = 和 §3 下钻重复。§0 只许讲父模块聚合统计（19 次尖峰 + 平均 43ms + 100% 命中慢帧），具体帧 + 子节点 ms 全部放 §3 下钻
- ❌ §0 ③ 的 narrative 写"worst frame 519 单帧 113.56ms"或"max frame 单帧 Xms"——具体帧的单帧数字总是和某个子节点尖峰绑定（frame 519 = GC.Collect 70ms 那帧），讲了 = 变相讲子节点尖峰细节 = 和 §3 下钻重复。§0 只许讲聚合统计（p50/p99/foldChange/占 p50%），具体帧的单帧 ms 全部放 §3 下钻
- ❌ §0 ③ 的引用写"详见 §3 下钻 ③（GC.Collect 单帧 70ms 是 worst frame 主因）"——引用不许带括号说明子节点 ms/帧号，只许写"详见 §3 下钻 ③"。括号里偷塞子节点细节 = 在引用里讲子节点细节 = 和 §3 下钻重复

**§0 的 ASCII 图和 §3 下钻的 callTree 子树区别**：
- §0 ASCII 图：摘要级（10 行内），三态/二态柱状图/因果链/演化对照，讲"演化趋势"（base→cur→throttle 涨了多少）——**不许用 ├─/└─ 缩进树**
- §3 下钻 callTree：完整子树（├─/└─ 缩进 + 每个节点的 ms/占比/标注），讲"具体哪个子函数贵、怎么治"
两者不重复——§0 讲趋势，§3 下钻讲细节。

## 章节骨架（§0-§4，对照 DR-43 多态方法论）

★【sections 必须建全 §0-§4 五章节·不许漏章】
你的 narrative.json sections 数组必须建全 5 个 section，每个 section 的 heading 以 §X 开头（如 "§1 采集元信息：..."）。
漏建任何一章 = 报告结构残缺。即使某章内容不多，也要建 section（intro 一句话 + 1 个 item 即可），不要跳过。

### §0 结论先行（多态版，全量结论叙事展开 + ASCII 图穿插，四段式）

§0 写**全量结论**（和 topConclusions 一一对应——topConclusions N 条就 §0 N 个 item），每条用四段式块（DR-41 规则 4）：
- 引用块 + 加粗一句话结论（人话，无字段名）
- ASCII 图（柱状/因果链/二态对照，数据源无关渲染工具产出）
- 关键数字解读（每条一行，数字配解读）
- 详见 §X 引用

★【§0 item 和 topConclusions 一一对应】
§0 的 items 数量 = topConclusions 数量。topConclusions N 条 → §0 N 个 item，每个 item 的 ①②③④... 编号和 topConclusions 的 rank 一一对应。
- topConclusions 是索引表（problem/kind/contribution/severity 4 列），§0 是叙事展开（人话+ASCII 图+详见 §X）
- 读者看 topConclusions 表扫一遍"有哪些问题"，读 §0 看每条结论的"为什么贵+影响多大+详见哪里"
- ❌ 反例：§0 只写 3 条，topConclusions 8 条——后 5 条只有表格行无叙事展开，读者看了 topConclusions #4-8 不知道为什么这些结论重要
- ✅ 正例：§0 写 N 条（N=topConclusions 数量），每条和 topConclusions rank 一一对应——全量结论都有叙事展开

★【§0 讲清"为什么贵"·允许讲子节点名字+占比·禁止子节点 ms/foldChange/GC alloc 数字】
§0 的叙事要讲清"为什么贵"——不能只讲"<父模块> 涨 ×N 倍"父模块摘要（读者看了不知道为什么 <父模块> 贵），要讲"<父模块> 涨 ×N 倍，大头是子节点 <大头子节点>（占 <父模块> 子树 X%）"——让读者知道父模块为什么贵。

**§0 允许讲**：
- 父模块自身的 foldChange + ms/帧 + 占 p50% + 绝对增量
- 子节点的**名字**（如"大头是 <大头子节点>"）+ **父子关系**（如"<父模块> 下大头子节点 <大头子节点>"）+ **占比**（如"占 <父模块> 子树 X%"）
- 子节点的"新出现/退化形态"定性描述（如"<大头子节点> 基线无当前新出现"）

**§0 不许讲**（v3 禁内容约束保留这部分）：
- 子节点的 ms/帧数字（如"<大头子节点> X.Xms"——这是 §3 下钻的职责）
- 子节点的 foldChange 数字（如"涨 ×N 倍"——这是 §3 下钻的职责）
- 子节点的 GC alloc 数字（如"GC alloc 0→N"——这是 §3 下钻的职责）
- 具体帧的单帧数字（如"frame #N 单帧 Xms"——这是 §3 下钻的职责）

**边界判定**：§0 讲"子节点名字+占比"是 OK 的（让读者知道为什么贵），讲"子节点 ms/foldChange/GC alloc 数字"是违规的（和 §3 下钻重复）。

★【§0 父模块 vs 子节点边界·父模块 = 红线清单条目】
§0 的"父模块"= §3 红线清单条目（如 PostLateUpdate.FinishFrameRendering）。红线清单条目下的子节点 ms 数字不许讲——即便子节点是"渲染管线"这种看起来像父模块的节点。
- ? 反例（v6 §0 ② URP 违规）：§0 ② narrative 写"每帧从 6.56ms 涨到 12.52ms（涨 1.91 倍），绝对增量 +5.96ms/帧"——这是 URP.RenderSingleCamera（子节点）的 ms 数字，不是父模块 PostLateUpdate.FinishFrameRendering 的 ms。§0 只许讲父模块自身的"涨 X 倍 + 占 p50 Y%"
- ? 反例（v6 §0 ② URP 违规）：§0 ② narrative 写"ForwardRenderPass 单帧尖峰 13.08ms @ frame 453（spikeRatio 5.13）"——这是子节点的具体帧单帧数字，§0 不许讲具体帧单帧数字
- ? 正例：§0 ② narrative 写"PostLateUpdate.FinishFrameRendering 涨 1.91 倍（临近红线），占当前 p50 29.9%，是稳态第二大成本——大头是子节点 URP.RenderSingleCamera（占父模块子树 90%），分摊型大头（10 个子 pass，maxChildRatio 0.28），统筹在父级"——讲父模块自身的 foldChange + 占 p50% + 子节点名字+占比+定性，不讲子节点 ms 数字

**注意**："看起来像父模块的子节点"也是子节点——URP.RenderSingleCamera 是 URP 渲染管线的统筹节点，但它是 PostLateUpdate.FinishFrameRendering（红线清单条目）的子节点，它的 ms 数字不许在 §0 讲。判断方法：看 §3 红线清单表格里列的是哪个模块名，那个模块才是 §0 的"父模块"，它的 foldChange + 占 p50% 可以讲；它下面的所有节点都是"子节点"，ms/foldChange/GC alloc 数字都不许讲。

❌ 反例 1（v3 禁过头）：§0 ① 只写"<父模块> 涨 ×N 倍，每帧多花 Xms"——读者不知道为什么 <父模块> 贵，要看 §3 下钻才知道是 <大头子节点> 涨 ×N 倍。§0 失去叙事价值，变成"父模块名+涨幅"的干瘪摘要。
✅ 正例 1（v5 松绑）：§0 ① 写"<父模块> 涨 ×N 倍（X→Y ms/帧），大头是子节点 <大头子节点>（占 <父模块> 子树 X%，基线无当前新出现）——是 <业务模块> 的回归主因"——讲清父模块为什么贵（子节点名字+占比+定性），但不讲子节点 ms/foldChange/GC alloc 数字。

❌ 反例 2（v4 残留）：§0 ① 的 ASCII 图写"<父模块>.<子入口> 每帧 ms: base ████ Xms / cur ████████████ Yms"——只画父模块 base vs cur，没讲为什么贵。读者看了不知道 <父模块> 里什么贵。
✅ 正例 2（v5 松绑）：§0 ① 的 ASCII 图画"<父模块> 子树大头分布: <大头子节点A> X% ████████ / <大头子节点B> Y% ████ / 其它 Z% ████"——画子节点占比分布，让读者一眼看到大头是谁。

★【§0 结论类型由 findings 自然浮现·不预设盯防】
§0 写什么类型的结论，由 findings 自然浮现，**不预设盯防**。典型维度（参考，不是约束——findings 里有什么就讲什么）：
- 最大涨幅模块（foldChange top N + 绝对增量 + 占当前 p50%）
- 新出现瓶颈（基线无 + 当前触红线）——只有 findings 里有才讲，没有不硬凑
- 退化形态（基线健康态 → 当前病态的形态变化）——只有 findings 里有才讲
- 稳态大头（每帧雷打不动的常驻税）
- 高频尖峰（多次出现的尖峰源）
- 低频尖峰（单次猛但帧数少）
- GPU bound / 降频 / GC / 工作线程退化 等

findings 里没有的维度，不硬凑。findings 里有的维度，按"对整体帧率贡献"排序讲。

★【§0 与 topConclusions 不重复·item.title 不许复述 problem】
§0 是"结论先行的叙事展开"——把 topConclusions 的结论用叙事方式讲出来（配 ASCII 图/关键数字/详见 §X）。
**不是 topConclusions 的复述**——topConclusions 是结构化表格（problem/kind/contribution/dimensions），§0 是人话叙事。
两者内容可以对应（都讲同一批结论），但表达形式不同：topConclusions 是表格行，§0 是四段式块。

**§0 item.title 必须和 topConclusions.problem 文本不同**——item.title 是叙事标题（人话+影响），不是 problem 的复述。
- ❌ 反例 1（v5 复述病）：topConclusions #1 problem="Lua 脚本更新模块退化：Update 路径涨 8.87 倍，每帧 14ms"，§0 ① title="① Lua 脚本更新模块退化：Update 路径涨 8.87 倍，每帧 14ms"——sim=1，完全复述，违规
- ✅ 正例 1：§0 ① title="① Update 路径退化是本次回归主因——Lua 脚本每帧多花 12ms 拖垮帧率"——换措辞+加影响，和 problem 文本不同
- ✅ 正例 2：§0 ① title="① Update 路径退化：从基线 1.57ms 涨到 14ms 的核心增量来源"——换角度+加数字解读，和 problem 文本不同
- 判定：如果 §0 item.title 去掉 ①②③ 编号后和 topConclusions.problem 的相似度 >0.8，就是复述，违规

★【多态判定用 foldChange + 绝对增量，不用占 p50%】
unity 多态有基线可对比，不用单态的"占 p50%"判定，用：
- foldChange ≥ 2（相对基线涨 2 倍以上）+ 绝对增量 ≥ p50 的 1%（防误判）→ 涨幅显著
- perFrameMs 占 p50 ≥ 5% + foldChange ≥ 2 → 触红线
- ≥3 态可用单调性增强信号（base→cur→throttle 是否单调下降/上升），2 态只能讲涨/跌

★【§0 每条必须有 ASCII 图·不许只有文字】
§0 每个 item 的四段式块必须有 ASCII 图——不许只有引用块+文字+详见 §X。
- ❌ 反例：§0 ② 只有引用块+文字段落+详见 §3 下钻 ②，没有 ASCII 图——读者看文字疲劳
- ✅ 正例：§0 ② 有引用块+ASCII 图（如尖峰时序图/柱状图）+关键数字+详见 §3 下钻 ②

**注意 DR-50 边界**：只给纪律"每条必须有 ASCII 图"不给内容"必须画什么类型"——画什么由 findings 决定。

### §1 采集元信息（多态：基线/当前 fps/p50/帧数对照表）

★ 本 section 的 item 必须填 `visualAsset`，type="table"，title="采集元信息"。
render 会把 visualAsset.table 渲染成表格放在 item 的 narrative 下方。

多态对照表（2 态和 ≥3 态兼容写法）：
- 2 态：表头 ["指标", "基线", "当前"]
- ≥3 态：表头 ["指标", "base", "cur", "throttle"]

item.visualAsset 填法（2 态示例）：
```json
{
  "title": "采集元信息",
  "type": "table",
  "table": {
    "headers": ["指标", "基线", "当前"],
    "rows": [
      ["采集窗口", "基线 11.4s / 当前 14.7s"],
      ["帧数", "基线 683 / 当前 483"],
      ["fps", "59.8 → 33.1"],
      ["p50", "16.69 → 30.15 ms"],
      ["p95", "18.20 → 42.54 ms"],
      ["p99", "21.37 → 66.32 ms"],
      ["slowFrameRate", "0% → 11.18%"],
      ["帧预算", "16.67 ms (60fps) / 33.33 ms (30fps)"],
      ["超预算帧占比", "0% → 100%"]
    ]
  }
}
```

item.visualAsset 填法（≥3 态示例）：
```json
{
  "title": "采集元信息",
  "type": "table",
  "table": {
    "headers": ["指标", "base", "cur", "throttle"],
    "rows": [
      ["采集窗口", "base 11.4s / cur 14.7s / throttle 19.9s"],
      ["帧数", "base 683 / cur 483 / throttle 427"],
```

## 写作纪律（DR-41 五条硬规则）

1. **报告 = 呈现层**：无 evidence id / tool name / 字段名（claim/boundary/relativeBaseline）
2. **子树归并**：同一子树的节点不重复出现在 top 列表（用 mergeBySubtree）
3. **结构 = 宏观 → 各线程 → 下钻**：不按 finding kind 罗列
4. **图文穿插四段式**：引用块 + ASCII 图 + 关键数字 + 详见 §X，禁止超过 3 行的文字段落
5. **人话先行**：技术数字沉底（narrative.json 的 findings[].claim + boundary），HTML 正文只有人话 + 关键数字

## 叙事形态（多态专用，DR-43）

- 演化型叙事：2 态用"从基线的 X 到当前的 Y——核心增量是 Z"；≥3 态用"从 base 的 X 经 cur 的 Y 演化到 throttle 的 Z"
- 多态对照表 + ASCII 柱状图 + foldChange 涨幅%
- 红线判定用 foldChange（相对倍数，不硬编码绝对阈值）+ 绝对增量（防误判，< p50 的 1% 不算回归）
- ≥3 态可用单调性增强信号（base→cur→throttle 是否单调下降/上升），2 态只能讲涨/跌

## unity vs perfetto 多态差异（避免硬搬 perfetto 模板）

| 维度 | perfetto 多态 | unity 多态（本模板） |
|---|---|---|
| 主线程入口 | UnityMain + atrace slice | PlayerLoop + marker |
| 帧分位数 | Android 帧时间线 + vsync 节拍 | PlayerLoop p50/p95/p99 + slowFrame |
| 多线程 | UnityMain/UnityGfxRenderS + Android 音频线程池 + sched | UnityMain/UnityGfxRenderS/Job.Worker/LuaMtGC + mainThreadWaits |
| GPU-bound | wait slice 重叠法 + byState S/R/D | mainThreadWaits + getThreadTimeline（主线程等谁） |
| 降频 | 大核 reach + 温度 + per-CPU | **无（unity 不暴露 CPU 频率，不写降频章节）** |
| GC 归因 | per-marker GC 分配（perfetto 独家） | queryFrameCounters gc_allocated_in_frame（整帧总量，无 per-marker） |
| 红线判定 | foldChange + perFrameMs | foldChange + 绝对增量 + perFrameMs（相同） |

**关键差异**：
- **unity 多态没有 perfetto 的降频/CPU 频率概念**——不写降频章节（perfetto §4 降频时序在 unity 多态下跳过，§0/§3 不提大核 reach/中核 max-freq/温度）
- **unity 多态没有 perfetto 的 off-CPU 归因/GPU-bound wait slice 重叠法**——主线程等待归因用 unity 的 mainThreadWaits + getThreadTimeline（主线程在等哪根线程），不写 byState S/R/D/R+ 分布
- **unity 多态没有 perfetto 的 Android 帧时间线/vsync 节拍**——用 PlayerLoop 分位数 + slowFrameRate
- **unity 多态的 GC 归因比 perfetto 弱**：queryFrameCounters 只有整帧 gc_allocated_in_frame 总量，给不了 per-marker 分配源（perfetto 有 per-marker GC 分配）——GC 卡顿根因分水岭（分配尖峰 vs 定时 GC）只能用整帧总量对照，诚实声明"per-marker 分配源需 DR-POOL-1 补"
- **unity 多态的 GPU-bound 判定比 perfetto 弱**：没有 wait slice 重叠法，只能用 mainThreadWaits 占比 + 渲染线程 run% + Semaphore/WaitForSignal marker 时序间接推断，诚实声明"单源无法断言 GPU 满载"
