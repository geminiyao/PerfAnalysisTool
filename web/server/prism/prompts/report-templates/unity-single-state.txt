# Unity 单态报告章节模板（DR-44 §3.2 第 2 层，对照 DR-42 单态方法论）

> 本模板定义 unity 单态报告的章节骨架，注入 narrative-prompt 的 {{REPORT_TEMPLATE}} 占位符。
> **和作文机的区别**：模板只定义章节结构 + 写作纪律，内容由 LLM 按 narrative-prompt 契约写。
> **不硬编码**业务名/绝对阈值/死模板（DR-41 + dev/conventions.md）。
>
> 单态适用场景：unity profiler 单源采集（无 base 对比，只有当前态）。
> 判定方法论对照 DR-42：用"相对占比"（占 PlayerLoop p50 百分比）+ "相对周期"（单次 vs vsync），不硬编码绝对 ms 阈值。
>
> **unity 特有概念可保留**：PlayerLoop / URP / MonoBehaviour / UnityMain / UnityGfxRenderS 等 unity 引擎概念是数据源特定的，模板里可写。
> **AOE 专属业务名不许出现**：游戏专属业务名（如各类 Mgr / 业务模块名）用占位符 `<模块名>` / `<业务模块A>` 等，不写死在模板里。

## 章节骨架（§0-§4，对照 unity 标杆 + DR-42 单态）

★【sections 必须建全 §0-§4 五章节·不许漏章】
你的 narrative.json sections 数组必须建全 5 个 section，每个 section 的 heading 以 §X 开头（如 "§1 采集元信息：..."）。
漏建任何一章 = 报告结构残缺。即使某章内容不多，也要建 section（intro 一句话 + 1 个 item 即可），不要跳过。

### §0 结论先行（3 条独立结论 + ASCII 图穿插，四段式）

写 3 条按强度排序的独立结论，每条用四段式块（DR-41 规则 4）：
- 引用块 + 加粗一句话结论（人话，无字段名）
- ASCII 图（柱状/缩进树/对照，数据源无关渲染工具产出）
- 关键数字解读（每条一行，数字配解读）
- 详见 §X 引用

典型维度（从 findings 自然浮现，不预设盯防）：
- 主线程瓶颈形态（PlayerLoop p50 占帧预算百分比 + 稳态/尖峰构成）
- 业务侧热点模块（perFrameMs 占 p50 百分比 + 单次 avg）
- 渲染/GC/交互尖峰（低频高冲击 marker，如相机移动/GC.Collect/资源卸载）

★【§0 与 topConclusions 不重复】
§0 是"结论先行的叙事展开"——把 topConclusions 的结论用叙事方式讲出来（配 ASCII 图/关键数字/详见 §X）。
**不是 topConclusions 的复述**——topConclusions 是结构化表格（problem/kind/contribution/dimensions），§0 是人话叙事。
两者内容可以对应（都讲同一批结论），但表达形式不同：topConclusions 是表格行，§0 是四段式块。
不许 §0 的 item.title 和 topConclusions 的 problem 文本高度相似——那是重复。

★【单态判定用相对占比，不用 foldChange】
unity 单态没有 base 对比，不用 foldChange（相对倍数），用：
- perFrameMs 占 PlayerLoop p50 百分比（≥5% 为热点）
- 单次 avg vs vsync 周期（≥vsync 50% 为红线）
- 累计 self ms（稳态大头看"每帧ms×出现帧数=累计总量"）

### §1 采集元信息（一张表）
★ 本 section 的 item 必须填 `visualAsset`，type="table"，title="采集元信息"。
render 会把 visualAsset.table 渲染成表格放在 item 的 narrative 下方。

item.visualAsset 填法：
```json
{
  "title": "采集元信息",
  "type": "table",
  "table": {
    "headers": ["指标", "值"],
    "rows": [
      ["帧数", "600"],
      ["fps", "23.9"],
      ["p50", "41.90 ms"],
      ["p95", "59.31 ms"],
      ["p99", "95.45 ms"],
      ["帧预算", "16.67 ms (60fps) / 33.33 ms (30fps)"],
      ["超预算帧占比", "100% 超 16.67ms / 100% 超 33.33ms"],
      ["PlayerLoop 总耗时", "25140 ms"]
    ]
  }
}
```
一张表：帧数/fps/p50/p95/p99/帧预算/超预算帧占比/PlayerLoop 总耗时。不硬编码具体数字（从 findings 取）。

### §2 多线程宏观（单态，所有线程 ms/帧 分布 + 线程间对比）

★ 本 section 的 item 必须填 `visualAsset`，type="table"，title="多线程宏观"。

- 每个识别到的 unity 线程一行：ms/帧 + 占主线程% + 关键 marker 特征 + 一句话定位
- 线程识别用 unity 通用名（UnityMain / UnityGfxRenderS / Job.Worker / LuaMtGC 等），不写 tid 硬匹
- 线程间对比定位（如 UnityGfxRenderS ms/帧 < UnityMain ms/帧 的 50% → 渲染线程在等主线程发命令）
- 排除项声明（如 Job.Worker ms/帧 极小不是瓶颈）

★【多线程覆盖必须全·不许合并线程】
findings 里 getThreadTimeline / queryUnityMarkers 查过的每个线程都要在 visualAsset.table 里有独立一行。
Job.Worker 1/2/3 等多线程各占一行，**不许合并成"Job.Worker 池"一行**——合并 = 丢内容（v4 退化教训）。

★【unity 单态没有 perfetto 的 Run/Sleep/Runnable%·用 ms/帧 代替】
unity 数据源没有 off-CPU sched 状态（Run/Sleep/Runnable 是 perfetto sched 独家）。
unity 用 getThreadTimeline 的 topLevelMs（每帧总耗时）+ queryUnityMarkers 的 thread 筛选做线程级画像。
**不许填 Run%/Sleep%/Runnable% 三列**——那三列 unity 给不了，填了只能填 "—"，等于丢内容。

item.visualAsset 填法：
```json
{
  "title": "多线程宏观",
  "type": "table",
  "table": {
    "headers": ["线程", "ms/帧", "占主线程%", "topMarker", "定位"],
    "rows": [
      ["UnityMain", "22.96", "100%", "PlayerLoop/Core.Update/<业务模块>", "主线程，业务/Lua/ECS 调度主入口"],
      ["UnityGfxRenderS", "11.52", "50.2%", "URP.Render/URP.Submit", "Unity 渲染命令录制层（ms/帧 < 主线程 50% → 等主线程发命令）"],
      ["Job.Worker.1", "0.42", "1.8%", "Burst Job 空闲", "Job 线程池，ms/帧 极小非瓶颈"],
      ["...其它 Job.Worker 各一行..."]
    ]
  }
}
```
ms/帧 从 getThreadTimeline 的 topLevelMs 取，占主线程% = 该线程 ms/帧 ÷ 主线程 ms/帧 × 100%。
topMarker 从 queryUnityMarkers(thread=该线程) 的 sortBy=selfMs top 1 取。不硬编码具体数字（从 findings 取）。

### §3 主线程一帧时间去向（callTree + 红线矩阵 + Top 模块下钻）

★ 本 section 的 item 必须填 `visualAsset`，type="table"，title="红线触发清单"。

- PlayerLoop 帧分位数对比表（p50/p95/p99/slowFrame/fps/帧数）
- 主线程 callTrees 缩进树（├─/└─ + [cur ms/帧] + 占 p50% + 严重程度标注）
  - 单态无 foldChange，用 perFrameMs 占 p50 百分比判定热点（≥5% 为红线）
- Top 红线热点子函数下钻（每个红线模块一张卡片：单次 avg + 红线判定 + GC 归因 + 优化方向）
- 红线触发清单（按 perFrameMs 占 p50% 排序，含模块/单次/红线类型/子函数热点）——填进 item.visualAsset (type=table)
- 慢帧形态差异（p95-p50 范围 + 匀慢/尖峰判定）

★【每个红线条目都要下钻·不只 Top 1】
红线触发清单里的每个模块都要有独立的下钻 item（给 callTree.rootMarker + narrative 讲内部拆分）。
**不许只给 Top 1 下钻，其它红线条目只列在表里不下钻**——v4 退化教训：只有 <大头子模块> 下钻，其它 5 个红线条目没下钻。
每个下钻 item 要讲：
- 该模块的 callTree 子树（子节点占比/热点）
- 红线判定（占 p50 百分比 / 单次 avg vs vsync）
- GC 归因（如果 findings 有 gcAllocByModule 数据）
- 优化方向（基于代码/数据推理，不许套话）

★【红线清单必须细到子模块·不许只到父级·统筹与拆出互斥】
redlineMatrix 的 module 列要细到子模块（如 <大头子模块>/<模块A>），
**不许只列父级 PlayerLoop 一行**——只到父级 = 丢内容（v4 退化教训）。
但也不许父子都列（DR-41 规则 2 子树归并，递归应用）——详见 narrative-prompt 的"红线清单子树归并原则"。
**统筹与拆出互斥**：对同一个父模块，要么统筹（列父模块 + hotspot 列子节点），要么拆出（列大头子节点 + 不列父模块）——不能同时列父模块和子节点。

item.visualAsset 填法（红线表，递归归并正确）：
```json
{
  "title": "红线触发清单",
  "type": "table",
  "table": {
    "headers": ["模块", "cur ms/帧", "占 p50%", "红线类型", "子函数热点"],
    "rows": [
      ["<模块A>", "3.80ms/帧", "12.51%", "占 p50 ≥5% 红线", "<大头子节点A1> 4.92% + <大头子节点A2> 3.99%（子节点统筹，不单独列）"],
      ["<大头子节点B1>", "1.575ms/帧", "5.19%", "占 p50 ≥5% 红线", "<叶子节点> (Burst) count=57820（父 <模块B> 不列，大头拆出）"],
      ["<渲染管线节点>", "10.64ms/帧", "35.43%", "占 p50 ≥5% 红线", "<子节点1> 40.43% + <子节点2> 38.12%"],
      ["...其它子模块各一行（不许父子同时列）..."]
    ]
  }
}
```

### §4 ROI 优化方向（按 severity + 贡献排序）

- 按 severity + 贡献排序的优化方向列表
- 每条：具体模块 + 问题 + 优化建议（基于代码/数据推理，不许套话）
- 优化方向要具体（不是"建议优化"，是具体的代码层建议，如"把 OnUpdate 内 head 信息每帧重建改成 dirty-flag 增量"）
- 单态 ROI 排序用"占 p50 百分比 + severity"（不用 foldChange）

★【优化建议必须基于源码·不许套话】
对进入主因的热点，给建议前必须先 getSourceForSymbol 看真实代码——建议要基于代码里实际看到的东西（已有/缺少哪些优化、有无每帧全遍历的循环等）。
看不到源码的（marker 无法锚定符号）就如实说"需要看 XX 的实现才能给具体建议"，别硬猜。
❌ 反例："建议单次任务削峰" / "考虑加缓存" / "降频处理"——没看代码的万能套话。
✅ 正例："OnUpdate 里三个每帧全量 foreach（m_targetToEffectDict/m_armyPredictDict/m_armyPreviewDict），改脏标记只在状态变化时处理"。

## 写作纪律（DR-41 五条硬规则）

1. **报告 = 呈现层**：无 evidence id / tool name / 字段名（claim/boundary/relativeBaseline）
2. **子树归并**：同一子树的节点不重复出现在 top 列表（用 mergeBySubtree）
3. **结构 = 宏观 → 各线程 → 下钻**：不按 finding kind 罗列
4. **图文穿插四段式**：引用块 + ASCII 图 + 关键数字 + 详见 §X，禁止超过 3 行的文字段落
5. **人话先行**：技术数字沉底（narrative.json 的 findings[].claim + boundary），HTML 正文只有人话 + 关键数字

## 叙事形态（单态专用，DR-42）

- 当前态型叙事："多信号同向验证当前态"（不用"演化型"）
- 单态判定用相对占比（perFrameMs 占 p50%）+ 相对周期（单次 vs vsync），不硬编码绝对 ms 阈值
- 无 foldChange（没有基线可对比），用占 p50 百分比 + 线程间对比定位热点
- **unity 单态没有 perfetto 的降频/CPU 频率概念**——不写降频章节（§4 降频时序在 unity 单态下跳过，§0/§3 不提 bigCoreReach/中核 max-freq）
- **unity 单态没有 perfetto 的 off-CPU 归因/GPU-bound wait slice 重叠法**——主线程等待归因用 unity 的 mainThreadWaits + getThreadTimeline（主线程在等哪根线程），不写 byState S/R/D/R+ 分布

## unity vs perfetto 单态差异（避免硬搬 perfetto 模板）

| 维度 | perfetto 单态 | unity 单态（本模板） |
|---|---|---|
| 主线程入口 | UnityMain + atrace slice | PlayerLoop + marker |
| 帧分位数 | Choreographer fps + frame timeline | PlayerLoop p50/p95/p99 + slowFrame |
| 多线程 | UnityMain/UnityGfxRenderS/AudioTrack/AAudio + sched | UnityMain/UnityGfxRenderS/Job.Worker/LuaMtGC + mainThreadWaits |
| GPU-bound | wait slice 重叠法 + byState S/R/D | mainThreadWaits + getThreadTimeline（主线程等谁） |
| 降频 | bigCoreReach + 温度 + per-CPU | 无（unity 不暴露 CPU 频率） |
| GC 归因 | gcAllocByModule（perfetto 独家） | queryFrameCounters gc_allocated_in_frame（整帧总量，无 per-marker） |
| 红线判定 | perFrameMs 占 p50% + 单次 vs vsync | perFrameMs 占 p50% + 单次 vs vsync（相同） |

**关键**：unity 单态的 GPU-bound 判定比 perfetto 弱（没有 wait slice 重叠法），只能用 mainThreadWaits 占比 + 渲染线程 run% + Semaphore/WaitForSignal marker 时序间接推断，诚实声明"单源无法断言 GPU 满载"。
