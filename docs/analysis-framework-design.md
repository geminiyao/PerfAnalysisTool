## 1. 为什么要多源采集（采集目的）

性能问题的根因散落在**三个正交的测量层级**上，任何单一工具都有结构性盲区。一次采集、多源对齐，本质是用三个互不重叠的视角观察同一次运行：

| 数据源 | 测量层级 | 回答的核心问题 | 独占能力（别的源拿不到） |
|--------|----------|----------------|--------------------------|
| Unity Profiler (.pdata) | 引擎语义层 | **What**：每帧各子系统花了多少时间？ | 精确帧边界、引擎语义归属（Physics/Render/GC/Job 线程每帧负载） |
| simpleperf | 原生指令/函数层 | **Where**：CPU 周期具体花在哪个函数？ | 运行时调用机制开销（虚表/icall/GC barrier）、native 黑盒内部、低开销全覆盖、全进程统一归因 |
| perfetto | OS 调度 / 硬件层 | **Why**：线程为什么没在跑？机器是什么状态？ | off-CPU 原因（等核/等 GPU/等锁）、CPU/GPU 频率与降频、调度状态、binder、热状态 |

> **核心原则**：多源方向一致 → 高置信结论；方向矛盾 → 必须先找原因（采样窗口 / 场景 / 降频 / 瓶颈转移），不能用单一源下结论。

采集的目的因此不是"测得更多"，而是**让每个性能现象都能被至少一个源解释、被多个源交叉校验**。

## 2. 两类分析方向

### 2.1 单点分析（基础）

- **输入**：一次采集的多源数据。
- **处理**：各源热点抽取 → 三源交叉关联 → 瓶颈类型判定。
- **产出 / 回答**："**现在瓶颈在哪、该优化什么**"（绝对值、面向优化动作）。

典型判定（单点即可给出）：
- 主线程 CPU 占满 + 热点集中在某 so/函数 → **CPU-bound**，给出热点清单。
- 主线程 Running 低但帧慢 → **等待型瓶颈**（GPU / 锁 / binder / IO）。
- CPU 频率显著低于额定 + 温度高 → **热降频**，数据本身可信度需打折。

### 2.2 对比分析

- **输入**：两次采集（A 基准 / B 待测）。
- **处理**：可比性校验 → 实体匹配 → 差异计算 → 显著性判定 → 归因。
- **产出 / 回答**："**这次改动有没有效、效果能否归因于预期原因**"（相对值、面向回归/收益）。

## 3. 两者的关系：共享地基 + 独立上层

**结论：对比分析复用单点分析的地基，但额外叠了一层独立逻辑——既不是"做好单点就水到渠成"，也不是"两套完全不同的思路"。准确说是"地基复用 + 上层新增"。**

### 3.1 共享的地基（单点做好，对比直接受益）

- 每个源的 "原始数据 → 归一化指标" 提取（热点、帧分布、调度状态…）。
- 三源交叉关联规则（CPU-bound / 等待型判定、帧口径校验）。

这部分对比 100% 复用，所以**单点是对比的必要前置**。

### 3.2 对比独有、单点用不上的新逻辑

1. **可比性校验（对比的命门）**：两次采集的场景 / 帧数窗口 / 设备 / 热状态必须对齐，否则 diff 全是噪音。单点没有"另一个基准"，根本不存在这个问题。
2. **实体匹配 / diff 语义**：函数在两份采样间的配对——优化常导致函数内联后"消失/新增"，需要"增 / 删 / 改"三态标记与子树归并。单点只需"列出热点"。
3. **显著性 / 噪音地板**：单点报"占 28%"是事实；对比报"降了 5pp"必须先回答"这是真改善还是采样抖动"，需要一个 delta 显著性模型（理想靠多次采集的方差估计）。
4. **回答的问题不同**：单点是绝对、面向动作；对比是相对、面向归因/回归。输出形态与受众都不同。

### 3.3 一句话

> 把单点分析做扎实，对比分析省掉一半工作量（地基）；但对比的"可比性、匹配、显著性、归因"是另起的一层，必须单独设计，不会自动得到。

### 3.4 差分视图的本质（决定"要不要为每个源都做差分"）

> **核心原则：差分视图不产生任何新的可观测性。它只能对"源本来就测到的东西"做减法。**

由此推论："A 源的差分能不能替代 B 源的差分"这个问题，**等价于**"A 源的原始数据能不能替代 B 源的原始数据"。而各源观测的是不同层级（见 [`data-sources-guide.md`](./data-sources-guide.md) §2.4），所以**差分视图之间同样不可互相替代**：

- **重叠区**（多源都测的指标，如帧时长 / Scripting 级耗时 / GC）→ 差分趋势应一致，作为**交叉校验**；若不一致，本身就是信号（例：marker 级耗时大降但函数级 self-time 几乎没变 → 改善来自调用次数/调度，而非计算量）。
- **非重叠区** → 每个源的差分都不可替代（marker 差分给"哪个子系统变了"，函数级差分给"代码里哪个函数/机制变了" + 内联消失证据）。

**判断"何时单源差分就够 / 何时必须上更细的源"：**

| 改动性质 | 单源差分够吗 | 说明 |
|----------|--------------|------|
| 纯游戏逻辑 / marker 层改动，只关心"哪个子系统改善" | 引擎语义源差分即可 | 更细的源是杀鸡用牛刀 |
| native / 运行时 / 编译器 / 第三方库层改动 | 否，必须函数级差分 | 引擎语义源看不进，差出来仍是黑盒增量 |
| 某子系统回归但 marker 看不出原因 | 否，需下钻到函数级 | 把 marker 的 delta 归因到具体机制 |
| 怀疑系统级干扰（降频/抢占/GPU/binder） | 否，需调度/硬件源差分 | 计算量没变但环境变了 |

**设计含义**：差分能力应**按源、按需**提供，而非"为每个源各做一套完整 diff UI"。统一对比层在共享指标上做交叉校验，在各源专属维度上提供可下钻的差分；这正是 §5 `PerfProfile` 坚持"按源保留数据 + 带来源标签"、而非过早压扁成统一指标的原因——压扁了，交叉校验与根因归属都会丢失。

## 4. 分层框架

重构目标：把"提取"与"分析"解耦，让单点和对比成为**同一套底座的两个消费者**。

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 3  对比分析层                                          │
│   输入 2 个 PerfProfile → 可比性校验 / 实体匹配 / 显著性 / 归因 │
│   产出：版本差异结论                                          │
├─────────────────────────────────────────────────────────────┤
│ Layer 2  单点分析层                                          │
│   输入 1 个 PerfProfile → 热点抽取 / 三源交叉 / 瓶颈定位       │
│   产出：瓶颈与优化方向                                        │
├─────────────────────────────────────────────────────────────┤
│ Layer 1  提取层（每源一个 Provider）                          │
│   UnityProfilerData / perf.data / .pftrace / <未来新源>       │
│   产出：统一的 PerfProfile 对象                               │
└─────────────────────────────────────────────────────────────┘
```

关键点：
- **Layer 1 是地基**。重构第一步是把 `PerfProfile` schema 定扎实，而不是先写分析逻辑。
- 单点 = Layer 1 + 2；对比 = Layer 1 + 3。两条路径共享 Layer 1。
- **新增数据源 = 新增一个 Layer 1 Provider**，Layer 2/3 不动（见 §7）。

## 5. 数据模型：Run = raw + core + detail

一次采集就是一个 **Run**。它打包三样东西，三者职责不同、存储策略不同：

```
Run = {
  raw    : 原始文件指针（真相源）  ── 大、可冷存/归档；深层联合差分时回读
  core   : 归一化指标（统一词汇表）── 小、物化入库；供单次展示 / 列表 / 趋势，解析一次读很多次
  detail : 各源专属富数据/产物    ── schemaless；火焰图/folded/SQL 等，多为产物文件指针
}
```

- **raw 是真相源**：可移到冷存储/CDN；只要它在，core 就能按需重算。
- **core 是物化的归一化视图**：把各源五花八门的原始字段，翻译成一套统一命名/单位（"归一化"），入库缓存。**只放需要跨源对比/关联/趋势的指标。**
- **detail 是开放扩展区**：各源原样塞，由该源专属 UI/skill 渲染；**新维度（GPU drawcall、内存堆树…）进这里，core 不动。**

### 5.1 core —— 归一化 + 指标袋（避免硬编码列）

```ts
interface PerfProfileCore {
  schemaVersion: number;            // 归一化逻辑升级后，可据此从 raw 重算
  // 指标袋：加指标 = 多一行，不改表结构（杜绝 il2cppBasePct 这类用例耦合的硬编码列）
  metrics: Metric[];
  // 帧口径必须显式标注；不同源各一条，禁止默认直比
  frame: { source: SourceId; frameDefinition: 'playerloop' | 'choreographer' | 'frametimeline';
           p50Ms: number; p95Ms: number; p99Ms: number; fps: number; slowFrameRate: number }[];
  threads: { source: SourceId; name: string; runningPct: number; runnablePct: number; sleepingPct: number }[];
  system: { cpuFreqAvgMhz?: number; cpuThrottled?: boolean; thermalC?: number;
            gpuBusyPct?: number; binder?: { count: number; avgMs: number }; pssMb?: number };
  confidence: { perFrameAlignmentOk: boolean; notes: string[] };  // 跨源帧偏差超阈值即告警
}

interface Metric {
  key: string;        // 统一命名：如 "cpu.lib.libil2cpp.pct" / "frame.p95Ms" / "system.wakeupLatencyMs"
  value: number;
  unit: 'ms' | '%' | 'pp' | 'mhz' | 'count' | string;
  source: SourceId;   // 来自哪个源
  confidence?: 'high' | 'medium' | 'low';
}
```

### 5.2 detail —— schemaless 原样留档（不归一化）

```ts
interface SourceDetail {
  unity_profiler?: unknown;   // topMarkers / callTree / frameDist …
  simpleperf?:     unknown;   // folded / flamegraphPath / 完整函数表 …
  perfetto?:       unknown;   // sqlResults / surfaceFlinger …
  [k: string]: unknown;       // 新维度进这里，永不撑爆 core
}

type SourceId = 'unity_profiler' | 'simpleperf' | 'perfetto' | string;
```

> 取舍记录：detail 之所以不归一化，是因为它们**没有跨源可比对象**（火焰图、SQL 结果），只给本源自己的面板看。归一化只对"要一起开会比较的内容"做。

### 5.3 对比分析的输入与执行（统一走深层）

- **对比 = 针对 2 个 Run 的数据做分析**。一个 Run 同时带 `core` 与 `raw/detail`。
- **统一走"深层联合"一条路径**（不分浅/深双路，避免实现分叉）：把两个 Run 的明细联合配对——函数匹配、差分火焰图、anchor 子树 diff；浅层标量差（帧 P95、so 占比）是联合过程的**副产品**，顺带得到。
- **core 不是为对比而存**：对比要明细时回读 detail/raw 现算（或读已缓存的 detail）。core 真正服务于 **单次展示 / Runs 列表 / Dashboard / 趋势**——其中**趋势是唯一硬依赖 core 的场景**（N 个版本不可能每次重解析）。
- 概念区分（仅作说明）：**浅层 = 两个数相减**（core 即可）；**深层 = 两边明细逐项配对/对齐整棵调用树**（需 detail/raw）。落地按"对比统一深层"。

## 6. 分析层与 skill 架构

把"出数据"与"分析"解耦：**确定性代码在下，AI 解读在上**。

```
① 出数据(代码 / Provider)   解析 → PerfProfile(core+detail)。可缓存、可复现、不耗 token。
② 算指标 / 算 diff(代码)     单次抽热点；对比做函数配对、算 delta、显著性阈值。确定性。
③ 解读(skill / AI)          对①②算好的结构化结果下结论。skill 读 PerfProfile，不读原始文件。
```

**skill 切分原则：按"源 + 1 个跨源"切（N+1），不按"源 × 模式"切**，否则筒仓会在 skill 层重生（组合爆炸）。

```
单源分析 skill（每源一个，管该源「单次 + 同源对比」的解读）
  ├─ unity-profiler-analysis    （已存在，范例）
  ├─ simpleperf-analysis
  └─ perfetto-analysis
跨源 skill（1 个，源无关）
  └─ cross-source-analysis      单 run 交叉验证(瓶颈定型) + 多 run 跨源对比归因
```

- **加新数据源 = 只加 1 个单源 skill**，跨源 skill 不动 → 线性扩展，不爆炸。
- **同源对比归到单源 skill**：对比两份 simpleperf 数据，需要的仍是 simpleperf 领域知识，与单次解读同一套专长。
- **计算与解读分离**：函数配对、算 delta、显著性阈值是代码；"这意味着什么、优化是否有效"才是 skill。**别让 LLM 去配对几千个函数。**

## 7. 重构指导原则

1. **用例透明**：框架代码 / schema / 文档不出现任何特定优化的关键字或预期（如"应下降 X pp"）。这类阈值属于"用例配置"，而非框架。
2. **数据源可插拔**：新增源只实现一个 Layer 1 Provider，产出 PerfProfile 片段；Layer 2/3 无需改动。
3. **可比性与显著性是对比层一等公民**：先校验"能不能比"，再算"差多少"，最后判"差异显不显著"。
4. **帧口径统一与告警**：跨源帧时长偏差超阈值 → 标记为低可信，而非默默取其一。
5. **降级而非报错**：任一源缺失/解析失败，PerfProfile 仍可用其余源完成分析，并在 `confidence.notes` 说明。
6. **结论先行、明细可展开**：对比的多层切分（so 占比 / anchor 子树 / 函数 diff）**必须先给普通话结论，再逐层展开**，不能直接把 Level 1/2/3 术语表甩给用户。可读性是一等需求，不是事后包装。

## 8. 待定问题

- 显著性判定缺少多次重复采样的方差数据，初期可能只能用经验阈值（如 delta > 3% 且方向一致才算）。是否引入"同配置多次采集"作为基准方差来源？
- `cpu.runtimeOverhead`（虚表/GC 等开销归因）依赖 simpleperf 符号与启发式聚合，先做到 so/函数级，运行时开销分类作为后续增强。
- 帧口径对齐告警的阈值与 UI 呈现方式待定。
- 新增数据源（SurfaceFlinger/FrameTimeline、Thermal、PMU 等，见 `data-sources-guide.md`）接入优先级待排。
