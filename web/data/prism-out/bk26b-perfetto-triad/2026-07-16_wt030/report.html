#问题类型对整体贡献严重度
1 GPU-bound 三态恶化（throttle 单次等 GPU 17.8ms 已超 vsync） 稳态大头 + 演化型 throttle 态主线程 38% 窗口时间在等 GPU，单次 17.8ms 已超 16.67ms vsync 周期；帧率从 base 60fps → cur 33fps → throttle 21fps 崩跌，98.83% 帧超预算，是帧率退化的首要成因 严重
2 SoC 热限流（大核频率被压到 59%、中核 max 频率下降） 加剧因素 + 演化型 throttle 态大核集群平均频率仅达理论上限 59.2%（base 74.9%→cur 75.6%→throttle 59.2% 暴跌），中核观测 max 从 2419MHz 被压到 2227MHz，温度三态都 ≥75°C；是 GPU-bound 的加剧因素而非独立主因，让 GPU 一起降频形成恶性循环 高
3 Core.Update 业务模块随场景加载涌现（行军+战斗压测，非性能退化） 场景差异澄清 cur/throttle 态 Core.Update 占 17-24%（throttle 3436ms），涌现 OutSideViewArmyLineMgr/BattleHeadMgr/MapSignificanceMgr 三个战斗+行军 marker；但 base 是空场景无这些模块，foldChange=9999 是场景差异不是退化；cur→throttle 同场景对照业务模块有升有降无系统性恶化，帧时暴增主因是 GPU wait 中
4 渲染管线持续 GC 分配（URP.BeforeRendering + OpaquePass） 长期风险（当前非主因） cur 态 GC 分配 208568 次（throttle 59518 次），URP.BeforeRendering + Inl_OpaquePass 每帧 130+129 次（cur）；但 GC.Collect 实际仅触发 cur 3次/throttle 1次，占总窗口 <0.4%，当前不是帧时主因，是长期堆压力风险 低

主题分群
§0 结论先行

三条按强度排序的独立结论，每条配 ASCII 图 + 关键数字 + 详见引用。整体故事：GPU-bound + SoC 热限流双重恶性循环，主线程越来越闲但帧越来越慢。

① GPU-bound 三态恶化：主线程从'几乎全程在算'演化到'半睡型'，核心增量是等 GPU 严重

主线程等 GPU 的时间随三态单调暴涨：base 仅占窗口 5.4%（单次 0.9ms，健康），cur 占 19.2%（单次 5.8ms，中等 GPU-bound），throttle 占 38.1%（单次 17.8ms，已超过 16.67ms vsync 周期）。throttle 态主线程近四成时间在干等 GPU 完成一帧的 swapchain 提交，这是帧率从 60fps 崩到 21fps 的首要成因。
三态 Run/Sleep 演化对照（buildTriadAsciiBar 产出）：
base ████████████████████████████████ ░░░ Run 86.94% / Sleep 12.04%
cur █████████████████████████ ░░░░░░░░ Run 77.82% / Sleep 20.40%
throttle ███████████████████ ░░░░░░░░░░░░░ Run 56.99% / Sleep 38.99%
关键数字：Gfx.WaitForPresent 占整窗口 base 5.4% → cur 19.3% → throttle 38.1%（Sleep 增量几乎 100% 是等 GPU）；单次 avg 0.9ms → 5.83ms → 17.8ms（throttle 已超 vsync 周期 16.67ms）。详见 §3。

优化建议
  1. 检查 URP.RenderCameraStack count=854（throttle 每帧约 2 个 camera），确认是否有不必要的多相机渲染
  2. 排查 URP.MainRenderingTransparent throttle 727ms（3.64%），透明渲染 pass 值得排查
  3. GPU-bound 根因（DrawCall 过多 / Shader 复杂 / 分辨率 / 渲染负载）需 GPU 侧数据（GPU counter / RenderDoc 截帧）才能定位，当前只能停在间接强信号档
② SoC 热限流：大核频率被压到理论上限 59%，中核 max 频率下降，温度 75-79°C 高

throttle 态 SoC 明显降频：大核集群平均频率仅达理论上限的 59.2%（严重低频），中核集群的观测 max 频率从 2419MHz 被压到 2227MHz（SoC 主动压低 max-freq 的间接证据）。三态温度都在 75°C 以上（base 采后 77°C、cur 79.8°C、throttle 76.7°C），符合热限流形态。这是 GPU-bound 的加剧因素——SoC 整体热限流让 GPU 也一起降频，形成恶性循环。
三态降频形态 ASCII（每态特征 + 形态名）：
base 凉机起步 → 快速升温进热保护区间 bigCoreReach 74.9% / 温度 Δ+11.7°C (形态: 升温期)
cur 起点已饱和 79.8°C bigCoreReach 75.6% / 温度 79.0°C (形态: 高温饱和)
throttle 持续 75-77°C 热稳态 bigCoreReach 59.2% / 中核 max 2227MHz (形态: 持续热限流)
关键数字：bigCoreReach base 74.9% → cur 75.6% → throttle 59.2%（暴跌至 <65%）；中核 max 2419→2342→2227MHz（被压低）；R+（被抢占）base 0.42% → throttle 2.78%（大核不足任务排队）。详见 §4。

源码归因未读到项目温控策略代码和画质档位配置；AOE3D 有 5 档画质，是否在温度超阈值时自动降档需看项目配置。
优化建议
  1. 短期：优先解决 GPU-bound（见 §0 ①），GPU 负载降下来温度自然降
  2. 长期：看是否有画质档位可动态降级（AOE3D 有 5 档画质），在温度超阈值时自动降档
  3. 检查渲染分辨率（移动端 900p）是否可在热态时动态下调
  4. 降频根因（整体功耗超标 vs GPU 单独发热）需 GPU 侧 counter 数据才能定位
③ Core.Update 业务模块随场景加载涌现：是场景差异不是性能退化 中

cur/throttle 态 Core.Update 占 17-24%（throttle 3436ms / 17.21%），是业务逻辑主入口。但 base 态 Core.Update 仅 1177ms（10.3%）且内部没有 OutSideViewArmyLineMgr/BattleHeadMgr/MapSignificanceMgr 这些 marker——说明三态是不同场景（base 空场景 vs cur/throttle 战斗+行军压测），业务模块的 foldChange=9999 是场景差异不是性能退化。cur→throttle 之间这些业务模块反而略降（BattleHeadMgr 731→471ms，MapSignificanceMgr 627→456ms），不是退化方向。
